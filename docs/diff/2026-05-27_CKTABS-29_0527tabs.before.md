# 0527tabs - canvas view tab independence and switch performance design

작성일: 2026-05-27

## 1. 목적

상자 편집 캔버스의 출력 뷰 버튼을 다음 네 개의 같은 위계 버튼으로 재정의한다.

- `data-canvas-owner-item="canvas-page-root-button-미리보기"`
- `data-canvas-owner-item="canvas-page-root-button-크기-및-위치"`
- `data-canvas-owner-item="canvas-page-root-button-속성"`
- `data-canvas-owner-item="canvas-page-root-button-속성2"`

`속성2`는 기존 `속성` 버튼의 단순 alias가 아니다. `크기 및 위치`와 `속성`이 서로 독립 view mode인 것처럼, `속성2`도 독립 view mode, 독립 상태, 독립 cache key, 독립 owner item을 가진다. 초기 기능은 `속성`과 동일하게 시작할 수 있지만, 같은 상태값을 공유하거나 같은 active/collapsed/selection state를 바라보면 안 된다.

동시에 현재 `크기 및 위치`와 `속성` 전환이 늦게 반영되는 원인을 제거한다. 브라우저 조사 결과, 탭 클릭이 단순한 view toggle이 아니라 live editor DOM 재정규화, auto-size 측정, peer edge/relative anchor 재계산, HTML 재직렬화, overlay 재측정을 다시 실행하고 있다. 목표는 탭 전환 시 이미 준비된 view별 파생 상태를 표시하도록 바꾸고, content/layout revision이 변하지 않은 상태에서는 무거운 재계산을 실행하지 않는 것이다.

이 문서는 설계 문서이며, 이 문서 작성 단계에서는 애플리케이션 코드를 수정하지 않는다. 후속 구현은 반드시 아래 실행 정책과 화이트리스트를 따른다.

## 2. 현재 이해 확정 목록

후속 구현자는 코드를 수정하기 전에 아래 내용을 사용자에게 다시 제시하고, 사용자가 명시적으로 확정한 뒤에만 수정한다.

- `속성2`는 `metadata`의 alias가 아니라 새 view mode이다. 권장 내부 값은 `metadata2`이다.
- `속성2`의 초기 UI와 동작은 `속성`과 같게 구현한다. 단, active 상태, overlay 접힘 상태, view cache, owner item, 선택 탭 식별자는 독립되어야 한다.
- `속성2`가 `속성`과 같은 계산 함수를 재사용하더라도, `metadata` cache/output/state를 fallback으로 읽으면 안 된다. `metadata2` view에는 `metadata2`로 생성된 prepared view만 렌더한다.
- `미리보기`, `크기 및 위치`, `속성`, `속성2`는 같은 위계의 view 전환 버튼이다.
- 상위 owner 버튼뿐 아니라 상자 편집 캔버스 내부 toolbar도 같은 정책을 따를지 확인한다. 현재 내부 toolbar는 `미리보기`가 별도 버튼이고 `크기 및 위치/속성`만 편집 설정 탭 그룹에 있다. 사용자의 "미리보기 역시 같은 위계" 요구는 내부 toolbar까지 같은 네 버튼 구조로 맞추는 방향으로 해석한다.
- `data-canvas-owner-item="canvas-container"`는 현재 브라우저 DOM에서 정확히 존재하지 않고 `canvas-container-2`, `canvas-container-48`처럼 자동 suffix가 붙는다. 후속 구현에서는 계약된 selector가 안정적으로 잡히도록 명시 owner item을 부여한다.
- 탭 전환 최적화는 기능 삭제가 아니다. auto height, peer edge, relative anchor, metadata relation, preview runtime 안정성은 유지하되 실행 시점을 content/layout 변경 revision에 묶는다.
- DB schema/data 변경은 현재 범위에 없다. DB 변경이 필요하다고 판단되면 즉시 중단하고 사용자 승인을 받아야 한다.

## 3. 실행 정책

아래 정책은 본 설계 또는 후속 수정에서 100% 준수한다. 구현 편의를 위해 축약하지 않는다.

### 3.1 수정 전 이해확정 절차

1. 후속 구현자는 코드 수정 전 "현재 요청 이해 확정 목록"을 작성한다.
2. 목록에는 구현할 버튼, 독립 상태 범위, 성능 개선 범위, 수정 파일 목록, 테스트 방법을 포함한다.
3. 사용자가 명시적으로 확정하기 전에는 어떤 코드도 수정하지 않는다.
4. 사용자의 확정 범위와 다른 변경이 필요해지면 즉시 중단하고 추가 승인을 받는다.

### 3.2 변경 기록 및 롤백 보장

1. 코드 수정 직전에 변경 대상 파일의 수정 전 상태를 `docs/diff`에 기록한다.
2. diff 기록에는 반드시 이 문서의 체크리스트 ID를 포함한다. 예: `2026-05-27_CKTABS-03_canvas-page.before.tsx`.
3. 새 파일 생성도 기록한다. 새 파일은 "파일이 존재하지 않았음"을 남기는 `.before.md` 문서를 만든다.
4. diff 기록 없이 코드 수정이 시작되면 즉시 중단한다.
5. diff 기록은 전체 파일 또는 수정 구간을 포함해야 하며, 사용자가 즉시 롤백할 수 있어야 한다.

### 3.3 확정 범위 외 수정 금지

1. 이 문서의 화이트리스트 밖 파일은 수정하지 않는다.
2. 화이트리스트 밖 파일 수정이 필요하면 즉시 중단하고 사용자 승인을 받는다.
3. 인코딩, 포맷팅, import 정리, linter 자동 수정도 확정 범위 밖이면 하지 않는다.
4. 변경 목적과 직접 관련 없는 refactor는 금지한다.

### 3.4 UI 변경 정책

1. 현재 서비스와 동일한 UI 디자이너가 만든 것처럼 기존 컴포넌트, 간격, 버튼 형태, 색상, typography를 따른다.
2. `/src/components` 폴더는 원칙적으로 수정하지 않고 참고한다.
3. 다만 이번 기능은 `TemplateEditWorkspace`, toolbar, preview surface 내부 view state가 직접 관련되어 있어 아래 화이트리스트에 최소 예외 파일을 명시한다.
4. 예외 파일에서도 목적 외 UI 구조 변경, 색상 변경, 불필요한 컴포넌트 교체는 금지한다.
5. 새 랜딩, 설명 카드, 장식 요소를 추가하지 않는다.

### 3.5 MCP 테스트 의무

1. 후속 구현 실행마다 `chrome-devtools` MCP로 실제 브라우저에서 확인한다.
2. 후속 구현 실행마다 `supabase` MCP를 실행한다. DB 변경이 없더라도 `get_advisors(type="security")`와 `get_advisors(type="performance")` 중 최소 하나를 실행하고 결과를 기록한다.
3. DB schema/data 수정이 필요하면 MCP로 직접 적용하지 않는다. SQL을 작성해 사용자에게 제공하고, 사용자가 직접 실행하도록 한다.
4. 테스트 수행 결과는 이 문서 하단의 테스트 기록 또는 후속 diff 문서에 남긴다.
5. Chrome 테스트는 단순 DOM 존재 확인으로 끝내지 않고, 최소한 view 전환 시간, mutation 규모, `data-canvas-owner-item` selector, `data-selection-panel-tab`, `data-canvas-owner-view-mode`를 확인한다.

## 5. 서비스 독립성 설계 원칙

이번 기능은 처음부터 별도 서비스로 분리 가능한 단위로 설계한다. "현재 React 컴포넌트 안에 두는 것이 빠르다"는 이유로 도메인 경계를 무너뜨리지 않는다.

### 5.1 Canvas View Mode Contract Service

#### 기능 목적

`preview`, `position`, `metadata`, `metadata2` view mode의 식별자, 라벨, owner item, 내부 tab key, 접근 가능성, fallback 규칙을 한 곳에서 계약화한다.

#### 단독 서비스로서의 가치

상자 편집 캔버스 외 페이지가 같은 view mode 계약을 사용할 수 있다. 향후 캔버스 view mode를 API 상품처럼 외부에서 제어할 때도 같은 DTO를 재사용할 수 있다.

#### 책임 범위

- view mode union 정의
- owner item 이름 계약
- label/description 계약
- view mode normalize
- view mode별 독립 state namespace 생성

#### 비책임 범위

- React render
- DOM mutation
- auto-size 실행
- preview HTML build
- DB 저장

#### API 계약

```ts
export type TemplateCanvasViewMode = 'preview' | 'position' | 'metadata' | 'metadata2';

export type TemplateCanvasViewTabKey =
  | 'preview'
  | 'position'
  | 'metadata'
  | 'metadata2';

export type TemplateCanvasViewModeDefinition = {
  mode: TemplateCanvasViewMode;
  tabKey: TemplateCanvasViewTabKey;
  label: string;
  description: string;
  ownerItem: string;
  metadataVisualMode: boolean;
  runtimePreviewMode: boolean;
};

export type NormalizeTemplateCanvasViewModeInput = {
  value: unknown;
  fallback?: TemplateCanvasViewMode;
};
```

#### 데이터 소유권

이 서비스는 view mode 계약만 소유한다. 선택된 frame, draft HTML, preview HTML, overlay collapsed state는 소유하지 않는다.

#### 의존 서비스

없음. 순수 DTO/정규화 서비스로 유지한다.

#### 분리 배포 시 최소 조건

TypeScript DTO 또는 JSON schema로 계약을 export할 수 있어야 한다. React 없이 단독 unit test가 가능해야 한다.

### 5.2 Canvas Derived View Cache Service

#### 기능 목적

각 view 출력에 필요한 파생 상태를 content/layout/selection revision 기준으로 미리 계산하고, 탭 클릭 시 재계산 없이 꺼내 쓸 수 있게 한다.

#### 단독 서비스로서의 가치

상자 편집 캔버스의 느린 전환 문제를 UI가 아니라 view state materialization 문제로 분리한다. 향후 worker, server-side precompute, remote cache로 확장 가능하다.

#### 책임 범위

- view별 cache key 생성
- contentRevision, layoutRevision, selectionRevision, settingsSignature 관리
- position view 파생 상태: position group, edge topology snapshot, relative anchor plan, spacing guide plan
- metadata view 파생 상태: metadata marker plan, relation connector plan, review warning plan
- metadata2 view 파생 상태: metadata와 같은 초기 계산을 별도 namespace로 저장
- preview view 파생 상태: runtime preview cache key와 build 준비 상태 추적

#### 비책임 범위

- live DOM 직접 변경
- React state 직접 변경
- DB 저장
- button render

#### API 계약

```ts
export type TemplateCanvasViewRevision = {
  draftRevision: number;
  layoutRevision: number;
  selectionRevision: number;
  settingsSignature: string;
};

export type TemplateCanvasViewCacheKey = {
  templateId: string;
  viewMode: TemplateCanvasViewMode;
  revision: TemplateCanvasViewRevision;
};

export type TemplateCanvasDerivedViewState = {
  key: TemplateCanvasViewCacheKey;
  viewMode: TemplateCanvasViewMode;
  ready: boolean;
  stale: boolean;
  overlayPlan: unknown;
  domPatchPlan: unknown;
  diagnostics: {
    computedAt: number;
    reason: string;
  };
};
```

필수 guard API:

```ts
export type TemplateCanvasPreparedViewMatchResult =
  | { ok: true; preparedView: TemplateCanvasDerivedViewState }
  | {
      ok: false;
      reason:
        | 'view-mode-mismatch'
        | 'revision-mismatch'
        | 'settings-signature-mismatch'
        | 'not-ready'
        | 'stale';
      requestedViewMode: TemplateCanvasViewMode;
      preparedViewMode?: TemplateCanvasViewMode;
    };

export const assertPreparedViewMatchesRequest = (
  requested: TemplateCanvasViewCacheKey,
  prepared: TemplateCanvasDerivedViewState | null
): TemplateCanvasPreparedViewMatchResult;
```

`assertPreparedViewMatchesRequest(...)`가 `ok: false`를 반환하면 UI는 prepared view를 렌더하지 않는다. 이때 다른 view의 결과를 "임시로" 보여주는 fallback은 금지한다.

#### 데이터 소유권

파생 view state와 invalidation signature를 소유한다. canonical editor draft는 소유하지 않고 입력으로만 받는다.

#### 의존 서비스

- Canvas View Mode Contract Service
- Runtime Preview Service
- 기존 edge/topology 계산 함수는 직접 import보다 DTO adapter로 감싼다.

#### 분리 배포 시 최소 조건

입력 HTML 또는 canonical frame DTO를 받아 view별 derived DTO를 반환할 수 있어야 한다. DOM이 없어도 cache key와 invalidation 판단은 test 가능해야 한다.

### 5.3 Runtime Preview Build Service

#### 기능 목적

`미리보기` 진입 시점에 runtime HTML을 즉시 새로 만드는 대신 draft/layout 변경 시 background로 prebuild하고 cache한다.

#### 단독 서비스로서의 가치

실제 사용 미리보기는 별도 서비스/API 상품화 가능성이 높다. editor DOM과 runtime output의 책임을 분리해야 preview가 editor geometry를 오염시키지 않는다.

#### 책임 범위

- editor draft hash 계산
- runtime preview build input DTO 정의
- `buildTemplateUsagePreviewHtml` 실행 시점 제어
- preview HTML cache
- attachment/signature/runtime field 초기화 정책

#### 비책임 범위

- editor DOM 직접 수정
- `setPreviewHtml` 직접 호출
- owner button render
- DB 저장

#### API 계약

```ts
export type RuntimePreviewBuildInput = {
  templateId: string;
  editorDraftHtml: string;
  draftHash: string;
  layoutSignature: string;
  options: {
    stabilizeInitialLayout: boolean;
    preventInitialValueClearShrink: boolean;
    measurePeerClusterHeightTargets: boolean;
    measurePeerClusterWidthTargets: boolean;
  };
};

export type RuntimePreviewBuildResult = {
  cacheKey: string;
  runtimeHtml: string;
  reused: boolean;
  builtAt: number;
};
```

#### 데이터 소유권

runtime preview HTML과 build cache를 소유한다. editor draft HTML은 입력으로만 받는다.

#### 의존 서비스

- Canvas View Mode Contract Service
- Canvas Derived View Cache Service

#### 분리 배포 시 최소 조건

HTML string input과 options만으로 runtime HTML을 반환해야 한다. React component state에 의존하면 안 된다.

### 5.4 Canvas Tab Presentation Adapter

#### 기능 목적

서비스 계약을 실제 owner page 버튼과 canvas toolbar 버튼에 연결한다.

#### 비책임 범위

- view cache 계산
- DOM 정규화

## 7. 현재 코드 원인

### 7.1 view mode가 독립 tab 상태로 유지되지 않음

현재 view mode 타입은 `preview | position | metadata`뿐이다.

- `src/components/template/workspace/types.ts`
  - `SelectionPanelTab = 'metadata' | 'position'`
  - `TemplateEditWorkspaceCanvasViewMode = 'preview' | 'position' | 'metadata'`

`TemplateEditWorkspace`는 `canvasViewMode`를 다시 `selectionPanelTab`으로 축소한다.

```ts
const canvasViewSelectionPanelTab =
  normalizedCanvasViewMode === 'metadata' ? 'metadata' : 'position';
```

이 구조에 `속성2`를 `metadata`로 매핑하면 두 버튼이 같은 tab state를 공유하게 된다. 사용자가 지적한 치명적 설계 문제가 여기서 발생한다.

### 7.2 상위 owner 전환과 내부 tab 전환이 2단계로 발생

`src/app/canvas/page.tsx`의 `handleSelectCanvasViewMode`가 owner settings를 바꾸고, 이후 `TemplateEditWorkspace` 내부 effect가 `selectionPanelTab`을 따라 맞춘다. 이로 인해 상위 owner state와 preview surface state가 한 번에 바뀌지 않는다.

현재 경로:

1. owner root 버튼 click
2. `settings.canvasViewMode` 변경
3. `CanvasOwnedWorkspace` props 갱신
4. `TemplateEditWorkspace`에서 `canvasViewSelectionPanelTab` 계산
5. effect/layoutEffect에서 `setSelectionPanelTab`
6. heavy rehydrate/layout effect 실행

개선 방향:

- view mode 자체를 workspace의 제어 상태로 인정한다.
- `selectionPanelTab`은 view mode의 alias가 아니라 view rendering adapter가 읽는 값이어야 한다.
- `metadata2`는 `metadata`로 축소하지 않는다.

### 7.3 tab switch에서 auto-size와 peer edge 경로가 다시 돈다

현재 `applyEditorAutoSizeBoxesWithPreservedLayout(root)`는 root 전체에서 auto-height frame을 수집한다.

```ts
collectFrameSelectionAnchors(root)
  .filter((frameNode) => readFrameAutoHeightBox(frameNode))
```

이 함수는 `selectionPanelTab !== 'position'` 경로에서도 실행된다. 따라서 `속성` 탭으로 전환하는데도 auto-height frame 전체를 다시 측정할 수 있다.

`position` 경로에서는 다음 작업이 같이 실행된다.

- `materializePositionGroupWrappers`
- `ensureRelativeAnchorConfigs`
- `normalizePositionGroupRelativeAnchors`
- `applyRelativeAnchoredFrameRectsInRoot`
- `applyEditorAutoSizeBoxesWithPreservedLayout`
- `buildLiveEdgeTopologySnapshot`
- `TemplateEdgeSelectionService.reconcileSelectionState`

이들은 content/layout 변경 시 필요한 작업이지, 단순 tab switch마다 필요한 작업이 아니다.

### 7.4 HTML 재직렬화와 surface 재삽입

`extractPreviewRenderHtml(root)`는 live root의 `innerHTML`을 복사한 뒤 정규화, attachment materialize, transient UI strip, selection attr strip 등을 수행하고 HTML string을 반환한다.

이후 `setPreviewHtml(nextRenderHtml)`이 실행되면 `TemplateEditPreviewSurface`의 `dangerouslySetInnerHTML`이 다시 들어간다.

탭 전환 중 content/layout revision이 바뀌지 않았는데 HTML 재삽입이 발생하면 불필요한 DOM churn이 생긴다.

### 7.5 preview mode도 클릭 시 runtime HTML build가 발생할 수 있음

`canvasViewPreviewRequested`가 true이고 `templateUsagePreviewHtml`이 없으면 layout effect에서 다음 작업을 즉시 수행한다.

- `syncFormControlMarkup(root)`
- `extractEditorHtml(root)`
- `buildTemplateUsagePreviewHtml(editorDraftHtml, options)`
- `setTemplateUsagePreviewHtml(runtimeHtml)`

즉 `미리보기`도 preloaded view가 아니라 activation-time build에 가까운 경로가 남아 있다.

## 8. 설계 방향

### 8.1 view mode 확장

권장 타입:

```ts
type TemplateEditWorkspaceCanvasViewMode =
  | 'preview'
  | 'position'
  | 'metadata'
  | 'metadata2';
```

`SelectionPanelTab`을 그대로 확장할지, 별도 `TemplateCanvasViewTabKey`를 만들지는 구현 전 확정한다. 권장안은 아래와 같다.

```ts
type SelectionPanelTab = 'position' | 'metadata' | 'metadata2';
type TemplateCanvasViewTabKey = 'preview' | SelectionPanelTab;
```

`preview`는 실제 사용 출력 모드이므로 `SelectionPanelTab`으로 취급하지 않는 것이 안전하다.

### 8.2 button definition은 value-only 배열 금지

현재 owner page는 `canvasViewModeOptions`가 value/label만 가진다. 후속 구현에서는 owner item을 명시한다.

```ts
const canvasViewModeOptions = [
  {
    value: 'preview',
    label: '미리보기',
    ownerItem: 'canvas-page-root-button-미리보기',
    description: '실제 사용 화면',
  },
  {
    value: 'position',
    label: '크기 및 위치',
    ownerItem: 'canvas-page-root-button-크기-및-위치',
    description: '크기와 위치',
  },
  {
    value: 'metadata',
    label: '속성',
    ownerItem: 'canvas-page-root-button-속성',
    description: '키/밸류 속성',
  },
  {
    value: 'metadata2',
    label: '속성2',
    ownerItem: 'canvas-page-root-button-속성2',
    description: '키/밸류 속성',
  },
] as const;
```

주의:

- `속성2` description은 초기에는 `속성`과 같아도 된다.
- `ownerItem`은 label에서 자동 생성하지 않는다.
- grid는 4개 버튼 기준으로 조정한다. 예: `sm:grid-cols-4`.

### 8.3 내부 toolbar 설계

현재 내부 toolbar는 `미리보기`가 별도 버튼이고, `크기 및 위치/속성`은 edit settings tab group이다.

요구사항을 엄격히 반영하면 내부 toolbar도 같은 view mode definition을 사용한다.

권장:

- `미리보기`
- `크기 및 위치`
- `속성`
- `속성2`

모두 같은 view mode command를 발생시킨다.

주의:

- preview는 실제 사용 preview mode이므로 편집 overlay를 숨긴다.
- `metadata2`는 `metadata`와 같은 UI를 초기 출력하되 `selectionPanelTab === 'metadata2'`로 식별한다.
- button shape 계산은 index/length 기반으로 바꾼다. 현재는 2개 버튼 기준 `first/last`만 쓰므로 3개 이상에서 middle 처리가 필요하다.

### 8.4 tab-only switch에서 금지할 작업

content/layout/selection revision이 바뀌지 않은 단순 view mode 전환에서는 다음 작업을 실행하지 않는다.

- `applyEditorAutoSizeBoxesWithPreservedLayout`
- `applyTemplateAutoSizeBoxesWithPreservedLayout`
- `extractPreviewRenderHtml`
- `setPreviewHtml`
- `buildLiveEdgeTopologySnapshot`
- `materializePositionGroupWrappers`
- `applyRelativeAnchoredFrameRectsInRoot`
- `buildTemplateUsagePreviewHtml`
- 전체 frame 대상 `querySelectorAll('.v202-frame-group[data-template-frame-group]')` 반복

단, 아래 작업은 가볍게 허용한다.

- root `data-selection-panel-tab` 갱신
- root `data-canvas-owner-view-mode` 갱신
- view별 overlay layer visibility toggle
- active button class/aria 갱신
- 이미 계산된 overlay plan 적용

### 8.5 revision 기반 invalidation

탭 전환 최적화의 핵심은 "계산하지 않음"이 아니라 "변경된 것만 계산"이다.

권장 revision:

- `draftRevision`: editor HTML 또는 frame content가 바뀔 때 증가
- `layoutRevision`: frame position, size, auto-size result, edge/anchor 구조가 바뀔 때 증가
- `selectionRevision`: selected frame group ids 또는 edge selection이 바뀔 때 증가
- `metadataRevision`: frame metadata draft, relation role, value key가 바뀔 때 증가
- `previewRuntimeRevision`: runtime preview build input이 바뀔 때 증가

view별 invalidation:

| view | invalidation 기준 | 전환 시 실행 |
| --- | --- | --- |
| `position` | `layoutRevision`, `selectionRevision`, position settings signature | cache hit이면 overlay 표시만 |
| `metadata` | `metadataRevision`, `selectionRevision`, metadata settings signature | cache hit이면 marker/overlay 표시만 |
| `metadata2` | `metadata2Revision`, `selectionRevision`, metadata2 settings signature | metadata와 독립 cache hit 사용 |
| `preview` | `draftRevision`, `layoutRevision`, runtime preview options signature | cache hit이면 runtime HTML 교체 없이 표시 |

### 8.6 metadata2 독립성

`metadata2`는 다음을 `metadata`와 공유하면 안 된다.

- active tab value
- overlay collapsed state
- view cache key
- relation connector render signature
- metadata visual mode signature
- user interaction mode state

공유해도 되는 것:

- metadata calculation helper
- role option list
- button visual component
- validation helper
- DTO schema

즉, 함수 재사용은 허용하지만 상태 identity 공유는 금지한다.

### 8.7 교차 view cache 사용 금지

이 절은 사용자의 우려를 막기 위한 핵심 불변 조건이다. "이미 준비된 화면을 보여준다"는 말은 각 view가 자기 이름으로 준비한 결과만 보여준다는 뜻이다. 다른 view에서 준비한 결과가 비슷해 보여도 대체 출력으로 사용할 수 없다.

#### 8.7.1 원본 데이터와 출력 결과의 분리

공유 가능한 것은 canonical 원본 데이터뿐이다.

- template id
- editor draft HTML 또는 canonical frame DTO
- frame group id 목록
- 저장된 metadata 값
- 저장된 position/layout 값
- 선택된 frame group id

공유 금지 대상은 view별 출력 결과이다.

- `position`용 edge button plan
- `position`용 relative anchor/position group overlay plan
- `metadata`용 marker/relation connector/role overlay plan
- `metadata2`용 marker/relation connector/role overlay plan
- `preview`용 runtime HTML
- overlay collapsed state
- render signature
- DOM patch plan
- prepared view cache entry

따라서 구현자는 "같은 원본을 읽어 각 view가 독립 출력물을 만든다"는 구조를 지켜야 한다. "metadata 출력물을 metadata2에서도 잠깐 보여준다"는 구조는 금지한다.

#### 8.7.2 cache identity 불변 조건

prepared view를 렌더하기 전에는 반드시 아래 조건을 모두 만족해야 한다.

```ts
preparedView.key.viewMode === requestedViewMode
preparedView.viewMode === requestedViewMode
preparedView.key.revision.draftRevision === requestedRevision.draftRevision
preparedView.key.revision.layoutRevision === requestedRevision.layoutRevision
preparedView.key.revision.selectionRevision === requestedRevision.selectionRevision
preparedView.key.revision.settingsSignature === requestedRevision.settingsSignature
preparedView.ready === true
preparedView.stale === false
```

하나라도 실패하면 해당 prepared view는 렌더 금지다.

#### 8.7.3 cache miss 처리 규칙

cache miss 또는 mismatch가 발생하면 다음 순서로 처리한다.

1. 현재 클릭한 버튼의 active state는 즉시 해당 view로 바꾼다.
2. 요청한 view의 prepared view가 없으면 해당 view 전용 pending state를 표시하거나, 기존 현재 view를 유지하되 새 view 결과라고 표시하지 않는다.
3. 요청한 view의 계산을 시작한다.
4. 계산 결과의 `viewMode`가 요청한 view와 정확히 일치할 때만 렌더한다.
5. 다른 view의 cache를 fallback으로 사용하지 않는다.

금지:

- `metadata2` cache miss 시 `metadata` 결과를 렌더
- `metadata` cache miss 시 `metadata2` 결과를 렌더
- `position` cache miss 시 마지막 `metadata` DOM patch를 유지한 채 `position` active로 표시
- `preview` cache miss 시 editor draft HTML을 runtime preview 완료 결과처럼 표시

#### 8.7.4 함수 재사용과 state 공유의 경계

허용:

```ts
const metadata2PreparedView = buildMetadataLikePreparedView({
  viewMode: 'metadata2',
  source: canonicalEditorModel,
});
```

금지:

```ts
const metadata2PreparedView = metadataPreparedView;
```

허용:

```ts
const metadata2OverlayPlan = buildMetadataOverlayPlan({
  namespace: 'metadata2',
  source: canonicalEditorModel,
});
```

금지:

```ts
const metadata2OverlayPlan = metadataOverlayPlan;
```

`buildMetadataLikePreparedView` 같은 계산 함수는 공유 가능하다. 하지만 함수 입력의 `viewMode`, `namespace`, `cacheKey`, `renderSignature`는 반드시 view별로 다르게 들어가야 한다.

#### 8.7.5 실패 시 사용자에게 보이는 상태

prepared view mismatch가 발견되면 조용히 옆 view를 보여주지 않는다. 후속 구현자는 아래 중 하나를 선택해야 한다.

- 해당 view 계산이 끝날 때까지 view surface를 pending 상태로 둔다.
- 기존 view surface를 유지하되 active 전환 완료처럼 보이지 않게 한다.
- 개발 모드에서는 mismatch reason을 console/debug panel에 기록한다.

어떤 경우에도 `속성2` 버튼이 active인데 실제 DOM이 `metadata` prepared view라는 상태를 만들면 안 된다.

#### 8.7.6 브라우저 검증 기준

Chrome MCP 테스트는 단순히 버튼이 보이는지 확인하지 않는다. 아래를 반드시 확인한다.

- `metadata` 클릭 후 rendered prepared view의 `data-canvas-prepared-view-mode`가 `metadata`인지 확인
- `metadata2` 클릭 후 rendered prepared view의 `data-canvas-prepared-view-mode`가 `metadata2`인지 확인
- `metadata2` cache를 비운 상태에서 `metadata` cache가 있어도 `metadata` 결과가 렌더되지 않는지 확인
- `metadata`와 `metadata2`의 overlay collapsed state를 각각 변경한 뒤 서로 영향을 주지 않는지 확인
- mismatch 상황에서 `assertPreparedViewMatchesRequest(...)`가 `view-mode-mismatch`를 반환하는지 확인

권장 DOM attribute:

```html
<div
  data-canvas-prepared-view-mode="metadata2"
  data-canvas-prepared-view-cache-key="..."
/>
```

이 attribute는 테스트와 디버깅을 위한 계약이다. 자동 생성 이름에 의존하지 않는다.

### 8.8 preview prebuild

현재 preview mode는 진입 시 runtime HTML을 만들 수 있다. 개선 후에는 다음 흐름을 사용한다.

1. draft/layout 변경 발생
2. runtime preview input hash 계산
3. idle task 또는 debounced task로 `RuntimePreviewBuildService.prebuild(input)` 실행
4. `preview` 버튼 클릭 시 cache hit 확인
5. cache hit이면 `templateUsagePreviewHtml`을 새로 build하지 않음
6. cache miss이면 fallback으로 build하되, 버튼 active 표시는 먼저 반영하고 build pending state를 명시적으로 관리

금지:

- preview 진입만으로 editor geometry를 수정하지 않는다.
- runtime preview auto-size 결과를 editor draft layout에 자동 commit하지 않는다.

## 10. 금지 구현 예시

아래 구현은 금지한다.

```ts
// 금지: 속성2를 metadata alias로 둠
{ value: 'metadata', label: '속성2' }
```

```ts
// 금지: metadata2를 metadata로 normalize
value === 'metadata2' ? 'metadata' : value
```

```ts
// 금지: view mode마다 독립 상태 없이 metadata UI만 조건 추가
const isMetadataLike = selectionPanelTab === 'metadata' || selectionPanelTab === 'metadata2';
const activeMetadataState = metadataState;
```

```ts
// 금지: metadata2 요청에서 metadata cache를 fallback으로 사용
const preparedView =
  cache.get(requestedMetadata2Key) ||
  cache.get(metadataKey);
```

```ts
// 금지: cache payload의 실제 viewMode를 확인하지 않고 렌더
if (preparedView.ready) {
  renderPreparedView(preparedView);
}
```

```ts
// 허용되는 형태: 요청 view와 prepared view identity가 정확히 일치할 때만 렌더
const match = assertPreparedViewMatchesRequest(requestedKey, preparedView);
if (match.ok) {
  renderPreparedView(match.preparedView);
} else {
  renderPreparedViewPendingState(match.reason);
}
```

`isMetadataLike` helper는 렌더 함수 재사용에는 사용할 수 있지만, state/cache/signature identity를 공유하는 근거로 쓰면 안 된다.

## 17. CKTABS-13 prepared view 보장형 재설계 보강

작성 시각: 2026-05-27 사용자 추가 지적 이후

### 17.1 정정 사항

이전 대화에서 언급된 "대규모 canonical store 전환"은 후속 구현의 1차 솔루션으로 채택하지 않는다.

이유:

- 현재 상자 편집 캔버스는 DOM, draft HTML, auto-size 계산, peer edge 계산, relation UI 계산이 얽혀 있다.
- canonical store를 한 번에 source of truth로 바꾸면 기존 기능이 정상 작동한다는 보장이 없다.
- 사용자의 요구는 실험적 재설계가 아니라, 현재 정상 동작을 보존하면서 속도 개선까지 보장하는 것이다.

따라서 후속 구현 원칙은 다음으로 확정한다.

- 기존 정상 계산 로직을 "정답 계산기"로 유지한다.
- 계산 로직을 새로 작성하지 않는다.
- 클릭, 입력, 드래그 순간에 정답 계산기를 동기 실행하지 않는다.
- 기존 정답 계산기가 만든 결과를 브라우저 메모리 prepared cache에 저장한다.
- 4개 view는 원본 값을 중복 저장하지 않고, 같은 브라우저 메모리 cache/revision을 기준으로 prepared projection만 따로 가진다.
- DB 통신은 최초 로드와 저장 버튼에서만 허용한다. 상자 편집 중 값 입력, 크기 변경, 위치 변경, 역할 변경, 탭 전환에서는 DB 저장/조회가 발생하면 실패로 본다.

### 17.2 보장해야 하는 결과

후속 구현은 아래 두 가지를 동시에 만족해야 한다.

1. 기능 정상 작동 보장
2. 속도 개선 보장

둘 중 하나만 만족하면 실패다.

기능 정상 작동 보장의 기준:

- 기존 계산 경로가 만든 결과와 prepared view 결과가 같아야 한다.
- 비교 단위는 문자열 전체 비교가 아니라 다음 계약 단위다.
  - frame group id
  - frame geometry: left, top, width, height
  - auto height/auto width 결과
  - peer edge 관계와 edge role
  - value key와 입력값
  - metadata role과 relation marker
  - position group wrapper
  - preview runtime control: input, file, signature
- prepared 결과가 기존 정답 계산기 결과와 다르면 그 prepared view는 표시하지 않는다.
- 불일치가 발생하면 `pending` 또는 `failed` 상태로 두고, stale view를 조용히 보여주지 않는다.

속도 개선 보장의 기준:

- prepared view가 ready인 tab 전환 handler는 10ms 미만이어야 한다.
- ready tab 전환에서는 runtime HTML build, auto-size, peer bounds 계산, 전체 HTML 추출, DB 호출이 없어야 한다.
- 값 입력 handler에서는 DB 호출 0회, 전체 `innerHTML` 교체 0회, 전체 frame tree scan 0회를 목표로 한다.
- 크기/위치 drag 중에는 숨은 view build를 중단하거나 지연한다.
- 숨은 view build는 idle/chunk 단위로 실행하고, slice budget은 3~5ms를 넘기지 않는다.
- 상자 변경 직후 hidden view가 아직 최신이 아니면, 전환 시 동기 계산하지 않고 즉시 pending을 표시한다.

### 17.3 "계산하지 않는다"의 의미 정정

"입력/크기 변경 handler 안에서 10ms 넘는 계산을 넣지 않는다"는 말은 계산을 생략한다는 뜻이 아니다.

정확한 의미:

- 반드시 필요한 현재 view의 계산은 한다.
- 다만 같은 사실을 4개 view에서 각각 다시 계산하거나 저장하지 않는다.
- 숨은 view의 무거운 표현 준비는 handler 안에서 하지 않는다.
- DB 통신, 전체 HTML 추출, preview runtime HTML 생성, hidden view auto-size 계산은 handler 밖으로 분리한다.

예를 들어 상자 높이가 변경되면:

1. 현재 view의 화면 높이와 관련 edge 표시를 즉시 맞춘다.
2. 같은 높이 값을 view별로 중복 저장하지 않는다.
3. 변경 revision을 브라우저 메모리 cache에 기록한다.
4. `position`, `metadata`, `metadata2`, `preview` prepared projection 중 영향받는 view를 dirty로 표시한다.
5. 현재 보고 있지 않은 view는 background에서 기존 정답 계산기로 준비한다.
6. 사용자가 dirty view로 이동하면 동기 계산하지 않고 pending을 보여준다.

### 17.4 브라우저 메모리 cache 계약

후속 구현은 브라우저 메모리에 아래 cache 계층을 둔다.

```ts
type CanvasPreparedViewMode = 'position' | 'metadata' | 'metadata2' | 'preview';

type CanvasPreparedViewStatus = 'ready' | 'dirty' | 'building' | 'pending' | 'failed';

type CanvasEditRevisionKey = {
  structureRevision: number;
  layoutRevision: number;
  valueRevision: number;
  metadataRevision: number;
  styleRevision: number;
  attachmentRevision: number;
};

type CanvasPreparedViewCacheEntry = {
  viewMode: CanvasPreparedViewMode;
  revisionKey: CanvasEditRevisionKey;
  status: CanvasPreparedViewStatus;
  html: string;
  validationSignature: string;
  preparedAt: number;
  buildSource: 'current-correct-calculator';
};
```

중요한 제한:

- 이 cache는 DB 저장소가 아니다.
- 이 cache는 독립 source of truth가 아니다.
- 이 cache는 현재 정답 계산기가 만든 prepared 결과 저장소다.
- 상자 원본 상태를 4개 view별로 따로 저장하지 않는다.
- prepared view별로 따로 가질 수 있는 것은 HTML/projection, overlay open state, pending/ready 상태뿐이다.
- height, width, left, top, value, role 같은 원본 값은 view별 중복 저장 대상이 아니다.

### 17.5 view 전환 정책

view 전환 시에는 아래 분기만 허용한다.

```ts
const entry = preparedViewCache.get(requestedViewMode);

if (entry?.status === 'ready' && revisionKeysEqual(entry.revisionKey, currentRevisionKey)) {
  showPreparedView(entry);
  return;
}

showPendingView(requestedViewMode);
schedulePreparedViewBuild(requestedViewMode, currentRevisionKey);
```

금지:

- view 클릭 순간 `buildTemplateUsagePreviewHtml(...)` 실행 금지
- view 클릭 순간 `extractPreviewRenderHtml(...)` 실행 금지
- view 클릭 순간 `applyTemplateAutoSizeBoxes(...)` 전체 실행 금지
- view 클릭 순간 DB 호출 금지
- cache miss 시 다른 view의 prepared result fallback 금지
- `metadata2` cache miss 시 `metadata` 결과를 보여주기 금지
- `preview` cache miss 시 editor HTML을 runtime preview인 것처럼 보여주기 금지

### 17.6 미리보기 pending 정책

미리보기는 다음처럼 동작해야 한다.

- `preview` prepared cache가 최신이면 즉시 preview surface를 표시한다.
- `preview` prepared cache가 dirty/building이면 즉시 pending surface를 표시한다.
- pending surface는 "미리보기 준비 중" 상태만 표시하고 계산을 동기 실행하지 않는다.
- background build가 완료되면 같은 requested view가 여전히 `preview`일 때만 preview surface로 교체한다.
- build 중 사용자가 다시 상자를 수정하면 기존 preview build는 abort 또는 obsolete 처리한다.
- obsolete build 결과는 절대 표시하지 않는다.

### 17.7 현재 기능 보존 전략

기능 보존은 "새 계산기를 믿는 방식"이 아니라 "기존 정답 계산기 결과와 비교하는 방식"으로 보장한다.

단계:

1. 기존 화면 계산은 그대로 둔다.
2. background에서 같은 입력으로 prepared view를 만든다.
3. 기존 정답 계산기 결과에서 validation signature를 만든다.
4. prepared view 결과에서도 validation signature를 만든다.
5. signature가 같으면 ready로 승격한다.
6. signature가 다르면 failed 또는 pending으로 유지하고 표시하지 않는다.

validation signature 예시:

```ts
type CanvasPreparedValidationSignature = {
  frameGeometryById: Record<string, { left: number; top: number; width: number; height: number }>;
  valueByKey: Record<string, string>;
  roleByFrameId: Record<string, string>;
  peerEdgesByFrameId: Record<string, string[]>;
  relationMarkersByFrameId: Record<string, string[]>;
  runtimeControlsByValueKey?: Record<string, 'input' | 'file' | 'signature'>;
};
```

signature 비교는 rounding/tolerance 규칙을 명시한다.

- geometry tolerance: 0.5px 이하
- string/value/role/relation: exact match
- runtime control type: exact match

### 17.8 상자 변경 처리 정책

상자 변경 이벤트는 아래 도메인 중 하나 이상을 dirty로 만든다.

- 상자 추가/삭제/타입 변경: `structureRevision`
- 크기/위치 변경: `layoutRevision`
- 값 입력: `valueRevision`
- 역할/속성 변경: `metadataRevision`
- 색상/테두리/폰트 변경: `styleRevision`
- 파일/서명 변경: `attachmentRevision`

처리 원칙:

- 현재 view에 필요한 최소 계산은 즉시 수행한다.
- 변경과 직접 관계없는 hidden view 계산은 실행하지 않는다.
- dirty marking은 즉시 한다.
- prepared build는 idle queue로 넘긴다.
- 같은 도메인 변경이 연속으로 들어오면 마지막 revision만 build한다.
- build 도중 더 최신 revision이 오면 이전 build result는 폐기한다.

## 21. CKTABS-19 documents/read 출력 복구 보완 설계

### 21.1 문제 정의

`49b8951f8945a00ec2fd435ed6d3e3e70a61f4d6` 기준에서는 `readMode` 출력이 단일 preview root를 사용했다.
`templateUsagePreviewActive`가 true여도 `surfaceRenderedPreviewHtml = templateUsagePreviewHtml || renderedPreviewHtml` 구조였기 때문에,
문서/read 화면은 runtime preview HTML이 아직 없어도 원본 문서 HTML을 화면에 즉시 표시할 수 있었다.

CKTABS-14~18에서는 탭 전환 성능 개선을 위해 editor room과 prepared preview room을 분리했다.
이 설계 자체는 유지해야 하지만, `readMode`가 같은 preview 활성 경로를 타면서 다음 순환 의존이 생겼다.

1. `readMode`이면 `templateUsagePreviewActive === true`가 된다.
2. `TemplateEditPreviewSurface`는 `templateUsagePreviewMode`가 true이므로 editor room을 숨긴다.
3. prepared preview room은 `templateUsagePreviewHtml`이 있어야만 mount된다.
4. `templateUsagePreviewHtml`은 `previewRef.current`에서 runtime HTML을 build해야 생성된다.
5. 하지만 `templateUsagePreviewMode` true 상태에서는 editor room이 active preview node로 등록되지 않아 `previewRef.current`가 비어 있다.
6. 결과적으로 runtime HTML을 만들 수 없고, runtime HTML이 없으므로 preview room도 만들 수 없다.

브라우저 확인 결과 `/canvas?page=documents&mode=read`에서 다음 상태가 확인됐다.

- `data-canvas-owner-item="canvas-container"`는 존재한다.
- editor room은 DOM에 있으나 `invisible`, `aria-hidden="true"`이다.
- prepared preview room은 없다.
- 캔버스 본문은 보이지 않고, 일부 편집 overlay 버튼만 출력된다.

따라서 문제는 설정 저장값 파괴가 아니라 “read/document 출력 view가 prepared preview room 계약에 제대로 등록되지 않은 것”이다.

### 21.2 절대 금지 사항

이번 복구는 기존 CKTABS-14~18의 즉시 전환 설계를 되돌리면 안 된다.
다음 방식은 금지한다.

- editor room과 preview room을 다시 하나로 합치는 것.
- `renderedPreviewHtml`을 template usage preview HTML로 직접 덮어쓰는 것.
- `미리보기`, `크기 및 위치`, `속성`, `속성2`의 선탑재 room 구조를 제거하는 것.
- 탭 클릭 시 runtime HTML build나 layout 재계산을 동기 실행하는 것.
- `readMode` 복구를 위해 template mode의 미리보기 pending/ready cache를 우회하거나 삭제하는 것.
- 숨겨진 editor room을 사용자에게 그대로 보여주는 것.
- `readMode`에서 편집 overlay/action panel을 노출하는 것.
- DB 저장/조회로 화면 전환 문제를 해결하려는 것.

### 21.3 보완 설계 핵심

`readMode`와 `documentMode`는 “사용자 미리보기 토글”이 아니라 “문서 사용 출력 view”이다.
따라서 template 편집 탭의 `preview` room과 같은 DOM 분리 원칙을 쓰되, lifecycle은 별도 계약으로 나눈다.

보완 후 view room은 다음 세 그룹으로 구분한다.

| room | 대상 | 생성 기준 | 표시 기준 | 비고 |
| --- | --- | --- | --- | --- |
| editor room | template 편집, position/metadata/metadata2 | `renderedPreviewHtml` | 편집 탭 활성 | CKTABS-18 유지 |
| template usage preview room | template mode 미리보기 탭 | `templateUsagePreviewHtml` ready/pending | 미리보기 탭 활성 | CKTABS-14~18 유지 |
| document usage output room | `documentMode`, `readMode` | document/read runtime HTML ready 또는 fallback shell | document/read 활성 | 새로 명시 |

중요한 차이는 다음이다.

- template mode preview는 사용자가 탭을 누르는 view 전환이다.
- document/read는 페이지 자체의 출력 목적이다.
- document/read는 시작 시점부터 출력 room이 있어야 하며, editor room이 숨겨져도 runtime HTML build source가 사라지면 안 된다.

### 21.4 구현 방향

#### 21.4.1 `previewRef` source deadlock 제거

현재 `readMode` runtime HTML build는 `previewRef.current`에 의존한다.
그러나 `templateUsagePreviewMode`가 true이면 editor root가 active preview node로 등록되지 않는다.

해결 방향:

- `TemplateEditPreviewSurface`는 editor root와 active preview root를 분리해서 상위에 전달한다.
- 상위 `TemplateEditWorkspace`는 다음 ref를 구분해 보관한다.
  - `editorPreviewRef`: 원본 editor DOM source
  - `activePreviewRef`: 현재 사용자에게 보이는 DOM
  - `preparedUsagePreviewRef`: prepared usage output DOM
- `documentMode/readMode` runtime HTML build는 `activePreviewRef`가 아니라 `editorPreviewRef`를 source로 사용한다.
- `activePreviewRef`는 포인터 이벤트, 선택, 첨부/서명 runtime interaction의 대상이다.

최소 구현 후보:

- `TemplateEditPreviewSurfaceProps`에 `setEditorPreviewNode?: (node: HTMLDivElement | null) => void` 추가
- `TemplateEditPreviewSurface`의 editor root mount 시 항상 `setEditorPreviewNode(node)` 호출
- `TemplateEditWorkspace`의 document/read runtime build effect는 `previewRef.current` 대신 `editorPreviewSourceRef.current || previewRef.current`를 사용

이 방식은 기존 `setPreviewNode` 의미를 “현재 활성 view”로 유지하면서, 숨겨진 source DOM만 별도 참조한다.

#### 21.4.2 document/read fallback shell 보장

`documentMode/readMode`에서 runtime HTML이 아직 준비되지 않았을 때 화면을 완전히 비우면 안 된다.

해결 방향:

- `documentMode/readMode`는 `templateUsagePreviewHtml`이 없더라도 `renderedPreviewHtml` 기반 fallback output room을 mount한다.
- fallback은 사용자 입력 가능 preview가 아니라 “준비 중에도 깨지지 않는 읽기 출력 shell”이다.
- runtime HTML이 준비되면 같은 room의 HTML을 교체하거나 prepared room을 표시한다.
- fallback 표시 중에는 편집 overlay/action rail을 숨긴다.

허용되는 fallback:

- `renderedPreviewHtml`을 read-only view shell로 잠시 표시
- “문서 출력 준비 중” pending overlay를 아주 짧게 함께 표시

금지되는 fallback:

- editor room 자체를 visible 처리해서 편집 overlay와 함께 보여주는 것
- `renderedPreviewHtml`을 `templateUsagePreviewHtml` state에 무조건 저장해서 preview cache를 오염시키는 것

#### 21.4.3 read/document와 template preview 상태 분리

현재 `templateUsagePreviewActive = documentMode || readMode || templateUsagePreviewMode || canvasViewPreviewRequested`가 너무 넓은 의미를 가진다.

보완 설계에서는 다음 파생 값을 분리한다.

- `usageOutputActive`: document/read 포함, 실제 사용 출력 view가 필요한 상태
- `templatePreviewTabActive`: template mode에서 사용자가 미리보기 탭을 선택한 상태
- `documentReadOutputActive`: `documentMode || readMode`
- `shouldHideEditorRoom`: template preview 또는 document/read output room이 표시되는 상태
- `shouldShowEditorOverlayRail`: template 편집 탭에서만 true

이름을 분리해야 이후 LLM이 `readMode`를 “사용자가 미리보기 탭을 눌렀다”와 혼동하지 않는다.

#### 21.4.4 overlay rail 노출 조건 복구

CKTABS-18에서 숨겨진 편집 room을 유지하려고 overlay props를 항상 넘겼다.
이로 인해 read 화면에서 편집 overlay 버튼이 보이는 문제가 생겼다.

해결 방향:

- overlay props는 “선탑재가 필요한 editor room”에는 남기되, 실제 overlay rail 표시 조건은 `shouldShowEditorOverlayRail`로 제한한다.
- `readMode/documentMode`에서는 overlay rail을 mount하지 않거나, mount하더라도 `aria-hidden`, `inert`, `hidden`으로 사용자 노출과 포인터 이벤트를 차단한다.
- `position/metadata/metadata2` 선탑재 room은 template editor active 상태에서만 보인다.

최소 구현 후보:

- `TemplateEditWorkspace`에서 `editorOverlayRailVisible = !documentMode && !readMode && !templatePreviewTabActive && editSettingsPanelVisible`
- `TemplateEditPreviewSurface`에는 `editSettingsPanelVisible={editorOverlayRailVisible}` 전달
- preview/editor room 선탑재 자체는 유지한다.

### 21.5 기존 기능 보존 검증 기준

구현 후 아래를 모두 만족해야 한다.

#### Template mode

- `미리보기`, `크기 및 위치`, `속성`, `속성2` 탭 버튼은 계속 즉시 반영된다.

- 탭 전환 중 `/api/` delta는 0이어야 한다.

- preview가 dirty/building이면 pending 표시를 유지한다.
- `position`, `metadata`, `metadata2` overlay rail room 선탑재 구조를 유지한다.

#### Documents read mode

- `/canvas?page=documents&mode=read`에서 문서 본문이 출력되어야 한다.
- editor room이 숨겨져 있더라도 document/read output room이 visible이어야 한다.
- 편집 overlay/action rail이 노출되면 안 된다.

- read-only, selection-only, attachment/signature runtime 상태가 기존처럼 적용되어야 한다.
- `data-canvas-owner-item="canvas-container"`는 유지되어야 한다.

#### Documents document mode

- 저장 가능한 document mode는 기존 저장/첨부/서명 동작을 깨지 않아야 한다.
- todo panel, save callback, editableValueKeys 계약을 유지한다.
- document mode에서 editor source ref와 active output ref가 뒤섞여 저장 HTML을 오염시키면 안 된다.

## 22. CKTABS-20 `속성2`를 `역할` 탭으로 재정의하는 보완 설계

### 22.1 변경 목표

이전 CKTABS-01~19에서 `속성2`는 `metadata2`라는 독립 view로 추가되었지만, 다음 구현부터는 사용자에게 보이는 모든 이름과 owner item을 `역할`로 바꾼다.
`역할` 탭은 `속성`의 복제 UI가 아니라, 선택한 상자에 역할을 부여하는 전용 작업 화면이다.

이번 설계는 다음 두 가지를 동시에 만족해야 한다.

1. `data-canvas-owner-item="canvas-container-상자-편집-탭-속성2"`는 런타임 UI에서 사라지고, 같은 위치의 버튼은 `data-canvas-owner-item="canvas-container-상자-편집-탭-역할"`이 된다.
2. `역할` 탭의 상자 선택 동작은 `/documents`의 `data-documents-owner-item="request-link-settings-column"` 화면에서 쓰는 상자 선택 동작과 같은 수준으로 동작해야 한다.

중요: `/documents` 수준의 선택이란 “상자를 클릭한 뒤 나중에 key를 찾아 활성화하는 후처리”가 아니다.
선택 가능한 target을 만들 때 이미 key/value 쌍을 하나의 선택 단위로 만든 뒤, 클릭과 드래그 중간 상태 모두에서 key와 value가 같은 선택 결과로 움직이는 방식이다.

### 22.2 이름 변경 계약

런타임 UI, owner item, 접근성 라벨, 테스트 selector, 사용자 문구에서 `속성2`는 `역할`로 변경한다.

변경 대상:

- 내부 toolbar 버튼
  - 기존: `data-canvas-owner-item="canvas-container-상자-편집-탭-속성2"`
  - 변경: `data-canvas-owner-item="canvas-container-상자-편집-탭-역할"`
  - label: `역할`
  - title/aria-label: `역할`
- owner root 설정 버튼
  - 기존: `data-canvas-owner-item="canvas-page-root-button-속성2"`
  - 변경: `data-canvas-owner-item="canvas-page-root-button-역할"`
  - label: `역할`
  - description: `선택 상자 역할 지정`
- owner settings 표시 문구
  - `canvasViewModeLabels.metadata2`의 사용자 표시값은 `역할`
  - `TEMPLATE_CANVAS_VIEW_MODE_DEFINITIONS`의 `metadata2` 표시 이름도 `역할`

- 저장된 owner setting 값 `metadata2`는 즉시 삭제하지 않는다. 기존 저장값과 cache key, view mode normalize를 깨면 이전 설정을 읽지 못한다.

- 후속 구현자가 내부 key까지 `role`로 바꾸려면 `metadata2 -> role` migration, normalize alias, 기존 저장값 복원 테스트를 별도 범위로 승인받아야 한다.

금지:

- `속성2` 텍스트를 버튼 label, title, aria-label, owner item, data attribute에 남기는 것.
- `역할` 버튼을 `속성` 버튼의 alias로 두는 것.

### 22.3 `/documents` 선택 수준의 실제 구조

브라우저에서 `/documents?documentId=2f6d0be2-8ba5-4d69-aacf-845275a66908`를 확인했다.
해당 화면은 `CanvasOwnedWorkspace`를 `workspaceMode="read"`로 열고, 오른쪽 설정 열은 `data-documents-owner-item="request-link-settings-column"`이다.

코드상 핵심 계약은 다음이다.

- `src/app/documents/_owner/DocumentsOwnerWorkspace.tsx`
  - `CanvasOwnedWorkspace`에 `canvasSelectablePolicy`, `selectedCanvasBoxes`, `onCanvasSelectionChange`를 전달한다.
  - `activeRequestSetupStep === 'box-assignee'`이면 `includeRoles: ['key', 'value', 'signature', 'attachment', 'text', 'unknown']`와 `selectableFrameGroupIds`를 전달한다.
  - `selectFieldsFromCanvasBoxes`는 `TemplateCanvasSelectedBox.valueKey`를 기준으로 선택 field를 확정한다.
  - `selectedCanvasBoxes`는 선택된 field를 다시 캔버스 highlight 상태로 돌려준다.
- `src/components/template/TemplateEditWorkspace.tsx`
  - `collectCanvasSelectionTargetItems(root, canvasSelectablePolicy)`가 실제 선택 단위를 만든다.
  - 기본 `linkedSelection`은 `key-value-pair`이다.
  - key 상자를 target으로 만들 때 연결된 value 상자 id들을 같이 모은다.
  - value 상자를 target으로 만들 때 `parentGroupId`로 key 상자를 같이 모은다.
  - `TemplateCanvasSelectedBox.highlightFrameGroupIds`에는 key/value id가 함께 들어간다.
  - `buildChecklistSelectableMarqueeHitEntries`는 target별 node rect union을 만들고, drag 중 hit된 target의 selection ids를 즉시 계산한다.
  - `applyChecklistSelectableMarqueeVisuals`는 pointer move 중 `selectedFrameGroupIdsRef.current`를 바로 key/value 묶음으로 바꾸고 `applyFastFrameSelectionUi`를 실행한다.
  - `emitChecklistSelectableTargets`는 click/drag 결과를 `onCanvasSelectionChange`로 내보내며, 이때 이미 key/value 묶음 정보가 포함되어 있다.

따라서 `/documents`의 선택 수준을 복제하려면 `역할` 탭도 같은 선택 target builder와 같은 marquee visual path를 써야 한다.
일반 편집 캔버스의 단일 frame 선택 후 `useEffect`나 선택 변경 handler에서 key를 찾아 추가하는 방식은 실패로 본다.

### 22.4 `역할` 탭 선택 설계

`역할` 탭은 `metadata2` view key를 호환용으로 유지하되, 동작은 `request-link-settings-column`의 선택 엔진을 template 편집 화면에 적용한다.

필수 동작:

- `역할` 탭 활성 시 선택 가능한 상자는 `collectCanvasSelectionTargetItems`로 미리 target화한다.
- 기본 policy는 `/documents`와 동일하게 `linkedSelection: 'key-value-pair'`로 둔다.
- key 클릭 시 key와 연결 value가 동시에 선택된다.
- value 클릭 시 value와 parent key가 동시에 선택된다.
- 드래그 선택 중에도 hit target의 `selectionIds`가 key/value 묶음으로 계산되어 즉시 visual selection에 반영된다.
- pointer up 이후에야 key를 찾아 추가하는 후처리 구현은 금지한다.
- `selectedFrameGroupIdsRef.current`와 visible selection UI는 pointer move마다 동일한 key/value 묶음으로 갱신되어야 한다.
- side panel의 active target도 `TemplateCanvasSelectedBox`의 `keyFrameGroupId`, `valueFrameGroupId`, `highlightFrameGroupIds`를 기준으로 정한다.

구현 방향:

- 현재 `TemplateEditWorkspace`의 checklist selectable controller는 `templateUsagePreviewActive`일 때만 붙는다.
- `/documents`는 read mode라서 이 조건을 통과한다.
- `역할` 탭은 template 편집 화면의 editor room에서 동작해야 하므로, controller 활성 조건을 아래처럼 확장한다.

```ts
const roleAssignmentTabActive = selectionPanelTab === 'metadata2' && !templateUsagePreviewActive;
const canvasLinkedSelectionControllerActive =
  checklistCanvasSelectionModeActive || roleAssignmentTabActive;
```

- 단순히 `checklistCanvasSelectionModeActive`를 true로 만드는 식으로 read/document 의미를 오염시키지 않는다.
- controller가 사용할 root는 현재 visible editor root여야 한다.
- role tab의 controller는 일반 `useCanvasPointerHandlers`보다 capture 단계에서 먼저 key/value target을 확정해야 한다.
- role tab에서 선택 가능한 target은 `canvasSelectablePolicy` prop이 없어도 자체 default policy를 만든다.

```ts
const roleAssignmentSelectablePolicy: TemplateCanvasSelectablePolicy = {
  includeRoles: ['key', 'value', 'signature', 'attachment', 'text', 'unknown'],
  linkedSelection: 'key-value-pair',
};
```

선택 결과 DTO:

```ts
type RoleAssignmentSelectedBox = TemplateCanvasSelectedBox & {
  keyFrameGroupId?: string;
  valueFrameGroupId?: string;
  highlightFrameGroupIds: string[];
};
```

이 DTO는 DOM id만 담고, role panel은 이 DTO를 읽어 역할 적용 command를 만든다.
height, position, value 같은 원본 상태를 복사해 저장하지 않는다.

### 22.5 `request-link-settings-column` 역할을 `역할` 탭으로 옮기는 방식

`request-link-settings-column`의 본질은 “캔버스 왼쪽, 설정 열 오른쪽, 선택 목록과 일괄 작업 컨트롤” 구조다.
`역할` 탭에서는 이 위계를 아래처럼 적용한다.

- 왼쪽: 상자 편집 캔버스 editor room
- 오른쪽: 역할 설정 column 또는 overlay rail room
- 상단: 현재 선택 수와 선택된 상자 목록
- 중간: 역할 부여 컨트롤
- 하단: 적용/초기화/검증 메시지

역할 부여 컨트롤은 기존 metadata 역할 계약을 우선 사용한다.

- `key`
- `value`
- `key_value`

필요 시 이후 단계에서 signature/attachment/text 같은 runtime kind assignment를 분리한다.
이번 설계의 기본 구현 범위는 “상자 metadata role 부여”이며, 요청 링크 담당자 지정/사진/파일 요청 생성 자체를 `역할` 탭에 복사하지 않는다.

적용 규칙:

- 선택 box가 key/value pair이면 panel의 선택 항목은 하나로 보이되, 내부 `highlightFrameGroupIds`는 key/value 둘 다 유지한다.
- `key` 역할을 적용하면 selected key target에만 role을 적용하고, 연결 value는 연결 대상 유지 여부를 검증한다.
- `value` 역할을 적용하면 value target의 `parentGroupId`, `valueKey` 계약을 함께 검증한다.
- `key_value` 역할을 적용하면 기존 parent 연결과 valueKey를 정리하는 기존 metadata role 변경 규칙을 따른다.
- 역할 적용은 기존 `applySelectionMetadataDraft` / `stageMetadataRole` 계열 command를 통해 canonical editor DOM에 반영한다.
- 역할 변경 후 dirty view는 `metadata2(role)`, `metadata`, `preview`만 표시하고, 탭 클릭 path에서 재계산하지 않는다.

금지:

- `/documents`의 assignee 저장 로직, request task 생성 로직, document API 호출을 `역할` 탭에 복사하는 것.
- 선택 후 별도 effect에서 key 상자만 active로 바꾸는 것.
- 선택 중에는 value만 보이다가 pointer up 이후 key가 추가되는 것.
- `metadata` 탭의 overlay room state를 `역할` 탭과 공유하는 것.

### 22.6 서비스 독립성 검토

기능 목적:

- `역할` 탭은 상자 선택과 역할 부여를 담당하는 독립 작업 view다.

단독 서비스로서의 가치:

- key/value pair 선택, 역할 부여, 역할 검증은 `/documents`, request link, template editor 외부에서도 재사용 가능한 도메인 기능이다.

책임 범위:

- selectable target 생성
- key/value linked selection
- selected box DTO 생성

비책임 범위:

- 문서 요청 링크 생성
- 담당자 저장
- DB 저장
- PDF 추출
- 위치/크기 편집

API 계약:


## 24. CKTABS-24 즉시 UI 보장 통합 보완 설계

### 24.1 보완 목적

`역할` 탭의 선택 이후 지연을 해결하면서 기존 CKTABS-14~23의 핵심 보장을 깨면 안 된다.

반드시 동시에 만족해야 하는 조건:

- 탭 전환은 계속 "이미 준비된 방을 즉시 보여주는 구조"여야 한다.
- `data-canvas-owner-item="canvas-container-상자-편집-탭"` 버튼 active 상태는 React commit을 기다리지 않고 즉시 바뀌어야 한다.
- 상자 값 입력, 크기 변경, 위치 변경, 역할 변경은 현재 보고 있는 view에 즉시 반영되어야 한다.
- 현재 보고 있지 않은 view는 즉시 재계산하지 않고 dirty 표시 후 background에서 준비한다.
- background 준비가 끝나지 않은 view로 전환하면 동기 계산을 하지 않고 해당 view 전용 pending을 표시한다.
- 탭 전환, 역할 선택, 값 입력, 크기/위치 변경, 역할 변경 중 `/api/` 또는 Supabase 요청이 발생하면 실패로 본다.
- DB 통신은 최초 로드와 명시 저장 버튼에서만 허용한다.

이번 보완의 기준은 "계산을 생략"이 아니다.
기존 정답 계산과 같은 결과를 만들되, 사용자 interaction handler 안에서 전체 view/부모 상태/DB를 다시 훑지 않도록 계산 위치와 소유권을 분리한다.

### 24.3 통합 즉시 UI 계약

모든 interaction은 아래 3단계로 분리한다.

1. Sync visual commit
2. Local canonical mutation
3. Deferred React/materialization commit

#### Sync visual commit

사용자 입력 handler 안에서 10ms 미만으로 끝나야 하는 영역이다.

허용 작업:

- 클릭된 탭 버튼의 `aria-pressed`, class, `data-canvas-toolbar-active-tab` 즉시 변경
- editor/preview/overlay rail room의 visibility/class 토글
- 현재 view의 DOM 값 또는 선택 visual 즉시 변경
- 미리 만들어진 hit/cache/map lookup
- dirty flag 기록
- background job enqueue

금지 작업:

- view HTML 재빌드
- auto-size 전체 재측정
- peer edge 전체 재계산
- `renderedPreviewHtml` 재직렬화
- hidden view 4개 동시 계산
- `flushSync`를 통한 대형 React tree commit
- `/canvas` owner 부모 state 갱신
- DB/API/Supabase 요청

#### Local canonical mutation

상자 값, 크기, 위치, 역할의 원본 상태는 브라우저 메모리 안의 단일 canonical state에만 반영한다.

원칙:

- 현재 view DOM은 canonical state의 즉시 projection이다.
- hidden view는 원본 상태를 따로 저장하지 않는다.
- hidden view는 prepared projection/cache만 가진다.
- canonical state 변경은 revision을 증가시키고 영향받는 prepared view를 dirty로 만든다.
- DB 저장은 canonical state를 저장 버튼에서만 serialize한다.

#### Deferred React/materialization commit

React state는 사용자 체감에 필요한 첫 paint 이후 정합화한다.

원칙:

- 정합화 작업은 `TEMPLATE_CANVAS_VIEW_REACT_COMMIT_DELAY_MS` 또는 idle queue로 이동한다.
- 같은 signature의 pending job은 합친다.
- 새 interaction이 들어오면 이전 stale job은 취소한다.
- 한 chunk가 10ms를 넘을 가능성이 있으면 target catalog build, panel option build, preview build, diagnostics build로 나눈다.
- React commit은 이미 DOM에 보인 결과를 덮어쓰지 않고 동일 signature인지 검증한 뒤 적용한다.

### 24.4 탭 전환 보장

기존 CKTABS-18/19 구조를 유지한다.

- `TemplateEditPreviewSurface`는 editor room, preview room, `position|metadata|metadata2` overlay rail room을 계속 선탑재한다.
- 탭 클릭 handler는 room visibility와 버튼 visual만 즉시 바꾼다.
- React의 `selectionPanelTab`, `canvasViewMode`, prepared status 정합화는 뒤에서 실행한다.
- 탭 클릭 경로에서 prepared view를 새로 만들지 않는다.
- cache miss이면 다른 view를 fallback으로 보여주지 않고 해당 view pending만 표시한다.

추가 보완:

- 미리보기 진입/복귀 뒤 발생하는 `188~471ms` long task는 탭 click path에서 완전히 분리해야 한다.
- preview build, document/read output build, runtime auto-size stabilization은 view click handler가 아니라 canonical revision 변경 또는 idle prebuild job에서만 실행한다.
- `position -> metadata2` first frame이 밀리는 사례는 역할 탭 진입 시 panel 계산이 click handler와 같은 frame에 섞인 것으로 보고, 역할 panel materialization을 deferred commit으로 이동한다.

탭 전환 성공 기준:

- click return `< 10ms`
- first visual frame `< 16ms`
- click 후 500ms 안 long task `0`
- `/api/` delta `0`
- requested view와 rendered prepared view의 mode mismatch `0`

- `roleTargetCatalog`
- `targetIdByFrameGroupId`
- `targetIdBySelectionId`
- `selectedBoxByTargetId`
- `selectionIdsByTargetId`
- `rectUnionByTargetId`

- 변경 없으면 즉시 종료

### 24.6 상자 수정 즉시 반영 보장

값 입력, 크기 변경, 위치 변경, 역할 변경은 현재 보고 있는 view에서 즉시 반영되어야 한다.

공통 정책:

- 현재 view에 보이는 값/위치/크기/역할은 handler 안에서 local canonical state와 current DOM projection에 즉시 반영한다.
- hidden view의 prepared projection은 dirty로 표시한다.
- hidden view 계산은 idle/background job으로 보낸다.
- hidden view가 아직 dirty인 상태에서 사용자가 전환하면 동기 계산하지 않고 pending을 표시한다.
- current view에 필요한 최소 auto-size/edge 보정만 실행한다.
- current view 보정도 10ms를 넘길 가능성이 있으면 affected frame group 단위로 쪼갠다.

값 입력:

- 입력값은 browser memory canonical value map에 즉시 반영한다.
- 같은 value를 `position`, `metadata`, `metadata2`, `preview` 네 곳에 따로 저장하지 않는다.
- 현재 DOM textarea/input 값은 브라우저 기본 입력 또는 immediate DOM projection을 신뢰한다.
- draft HTML serialize는 입력마다 실행하지 않는다.
- 저장 버튼 또는 background snapshot job에서만 serialize한다.

크기/위치 변경:

- 현재 frame group의 geometry만 canonical layout map에 즉시 반영한다.
- peer edge, relative anchor, auto-size 영향 범위는 dependency graph로 affected ids만 계산한다.
- 전체 page frame rect 재측정은 금지한다.
- hidden view의 guide/edge overlay는 dirty로 표시하고 background에서 재준비한다.

역할 변경:

- role, boxKind, parentGroupId, valueKey 변경은 canonical metadata map에 즉시 반영한다.
- 현재 `역할` panel과 선택 상자 visual만 즉시 갱신한다.
- `metadata`, `preview`, `document/read output` projection은 dirty로 표시한다.
- 역할 변경 후 DB 저장/조회는 금지한다.

입력/수정 성공 기준:

- input/resize/position/role handler dispatch `< 10ms`
- current view 첫 반영 `< 16ms`
- `/api/` delta `0`
- hidden view dirty marking `< 1ms`
- hidden view background job chunk `< 10ms`
- 저장 버튼 전까지 DB write `0`

### 24.7 중복 호출 및 DB 요청 제거 설계

interaction 중 네트워크 요청 금지:

- 탭 전환
- 역할 선택
- 값 입력
- 크기 변경
- 위치 변경
- 역할 변경
- preview pending/ready 전환

허용 네트워크:

- 초기 template/document load
- 사용자가 명시적으로 누른 저장 버튼
- 사용자가 명시적으로 요청한 파일 업로드/다운로드

브라우저 cache 사용 원칙:

- template/document initial payload는 canonical memory store에 적재한다.
- view prepared cache는 canonical revision key로만 invalidation한다.
- cache miss가 발생해도 interaction handler 안에서 DB/API로 값을 다시 가져오지 않는다.
- cache miss 시 pending을 표시하고 background job이 현재 canonical state로 projection을 만든다.

중복 job 제거:

```ts
type CanvasInteractionJobSignature = {
  jobKind: 'role-selection-panel' | 'preview-build' | 'metadata-overlay' | 'position-overlay' | 'document-output';
  viewMode: TemplateCanvasViewMode;
  draftRevision: number;
  valueRevision: number;
  layoutRevision: number;
  metadataRevision: number;
  selectionRevision: number;
  settingsSignature: string;
};
```

동일 signature job은 하나만 유지한다.
새 revision이 들어오면 이전 revision job은 stale 처리한다.
stale job 결과는 DOM/React state에 적용하지 않는다.

검증 guard:

- 모든 interaction 테스트는 시작 전/후 `performance.getEntriesByType('resource')`에서 `/api/` delta를 확인한다.
- fetch/XMLHttpRequest monkey patch probe를 추가해 Supabase/rest 호출도 잡는다.
- DB 요청이 발생하면 테스트 실패로 기록한다.
- cache hit/miss와 pending 전환은 `data-canvas-prepared-view-*` attribute로 확인 가능해야 한다.

## 26. CKTABS-26 scope picker DB source 분리

### 26.1 요청 이해

- `data-documents-owner-item="scope-picker-control-dropdown"`는 DB에서 불러온 scope 목록을 출력하는 리스트여야 한다.
- `data-canvas-owner-item="canvas-role-settings-scope-display-name-input"`에 값을 입력하거나 blur commit을 해도, 저장 전 draft 이름이 picker/dropdown list에 섞이면 안 된다.
- 사용자가 `scope 저장`을 실행하고 DB 저장이 성공하면, 저장 응답으로 다시 구성한 DB 기준 값이 picker/dropdown에 반영되어야 한다.

### 26.2 원인

- 기존 구현은 `scopePickerOptions`를 `scopeDraftSnapshot.logicalScopes`에서 만들었다.
- `scope-display-name-input` blur commit은 `scopeDraftSnapshot`의 `displayName`을 바꾸므로, DB 저장 전 draft 이름이 picker control과 dropdown list에 즉시 반영됐다.
- 이는 "picker/dropdown은 DB에서 불러온 목록"이라는 역할과 "edit input은 저장 전 draft"라는 역할이 섞인 상태였다.

### 26.3 구현 내용

- `scopeDraftSnapshot`과 별도로 `scopePersistedSnapshot` 상태를 추가했다.
- `scopePersistedSnapshot`은 다음 경우에만 갱신한다.
  - `/api/scopes/template-scopes` GET 성공으로 DB scope context를 불러온 경우
  - `/api/scopes/template-scopes` POST 저장 성공 응답을 받은 경우
  - 템플릿 없음/로드 실패로 scope context를 비우는 경우
- `scopePickerOptions`는 `scopePersistedSnapshot.logicalScopes`에서만 만든다.
- `scope-display-name-input`, `scope-description-input`, scope 조건 입력 등 편집 UI는 계속 `scopeDraftSnapshot`을 사용한다.
- 따라서 저장 전 draft 변경은 edit input과 save 가능 상태에만 반영되고, picker/dropdown DB 목록에는 반영되지 않는다.
- 저장 성공 후에는 POST 응답을 `createCanvasScopeDraftSnapshot(payload.data)`로 정규화해 `scopePersistedSnapshot`과 `scopeDraftSnapshot`에 동시에 반영한다.
