# 0527tabs - canvas view tab independence and switch performance design

작성일: 2026-05-27

## 1. 목적

상자 편집 캔버스의 출력 뷰 버튼을 다음 네 개의 같은 위계 버튼으로 재정의한다.

- `data-canvas-owner-item="canvas-page-root-button-미리보기"`
- `data-canvas-owner-item="canvas-page-root-button-크기-및-위치"`
- `data-canvas-owner-item="canvas-page-root-button-속성"`
- `data-canvas-owner-item="canvas-page-root-button-속성2"`

`속성2`는 기존 `속성` 버튼의 단순 alias가 아니다. `크기 및 위치`와 `속성`이 서로 독립 view mode인 것처럼, `속성2`도 독립 view mode, 독립 상태, 독립 cache key, 독립 owner item을 가진다. 초기 기능은 `속성`과 동일하게 시작할 수 있지만, 같은 상태값을 공유하거나 같은 active/collapsed/selection state를 바라보면 안 된다.

동시에 현재 `크기 및 위치`와 `속성` 전환이 늦게 반영되는 원인을 제거한다. 브라우저 조사 결과, 탭 클릭이 단순한 view toggle이 아니라 live editor DOM 재정규화, auto-size 측정, peer edge/relative anchor 재계산, HTML 재직렬화, overlay 재측정을 다시 실행하고 있다. 목표는 탭 전환 시 이미 준비된 view별 파생 상태를 표시하도록 바꾸고, content/layout revision이 변하지 않은 상태에서는 무거운 재계산을 실행하지 않는 것이다.

이 문서는 설계 문서이며, 이 문서 작성 단계에서는 애플리케이션 코드를 수정하지 않는다. 후속 구현은 반드시 아래 실행 정책과 화이트리스트를 따른다.

## 2. 현재 이해 확정 목록

후속 구현자는 코드를 수정하기 전에 아래 내용을 사용자에게 다시 제시하고, 사용자가 명시적으로 확정한 뒤에만 수정한다.

- `속성2`는 `metadata`의 alias가 아니라 새 view mode이다. 권장 내부 값은 `metadata2`이다.
- `속성2`의 초기 UI와 동작은 `속성`과 같게 구현한다. 단, active 상태, overlay 접힘 상태, view cache, owner item, 선택 탭 식별자는 독립되어야 한다.
- `속성2`가 `속성`과 같은 계산 함수를 재사용하더라도, `metadata` cache/output/state를 fallback으로 읽으면 안 된다. `metadata2` view에는 `metadata2`로 생성된 prepared view만 렌더한다.
- `미리보기`, `크기 및 위치`, `속성`, `속성2`는 같은 위계의 view 전환 버튼이다.
- 상위 owner 버튼뿐 아니라 상자 편집 캔버스 내부 toolbar도 같은 정책을 따를지 확인한다. 현재 내부 toolbar는 `미리보기`가 별도 버튼이고 `크기 및 위치/속성`만 편집 설정 탭 그룹에 있다. 사용자의 "미리보기 역시 같은 위계" 요구는 내부 toolbar까지 같은 네 버튼 구조로 맞추는 방향으로 해석한다.
- `data-canvas-owner-item="canvas-container"`는 현재 브라우저 DOM에서 정확히 존재하지 않고 `canvas-container-2`, `canvas-container-48`처럼 자동 suffix가 붙는다. 후속 구현에서는 계약된 selector가 안정적으로 잡히도록 명시 owner item을 부여한다.
- 탭 전환 최적화는 기능 삭제가 아니다. auto height, peer edge, relative anchor, metadata relation, preview runtime 안정성은 유지하되 실행 시점을 content/layout 변경 revision에 묶는다.
- DB schema/data 변경은 현재 범위에 없다. DB 변경이 필요하다고 판단되면 즉시 중단하고 사용자 승인을 받아야 한다.

## 3. 실행 정책

아래 정책은 본 설계 또는 후속 수정에서 100% 준수한다. 구현 편의를 위해 축약하지 않는다.

### 3.1 수정 전 이해확정 절차

1. 후속 구현자는 코드 수정 전 "현재 요청 이해 확정 목록"을 작성한다.
2. 목록에는 구현할 버튼, 독립 상태 범위, 성능 개선 범위, 수정 파일 목록, 테스트 방법을 포함한다.
3. 사용자가 명시적으로 확정하기 전에는 어떤 코드도 수정하지 않는다.
4. 사용자의 확정 범위와 다른 변경이 필요해지면 즉시 중단하고 추가 승인을 받는다.

### 3.2 변경 기록 및 롤백 보장

1. 코드 수정 직전에 변경 대상 파일의 수정 전 상태를 `docs/diff`에 기록한다.
2. diff 기록에는 반드시 이 문서의 체크리스트 ID를 포함한다. 예: `2026-05-27_CKTABS-03_canvas-page.before.tsx`.
3. 새 파일 생성도 기록한다. 새 파일은 "파일이 존재하지 않았음"을 남기는 `.before.md` 문서를 만든다.
4. diff 기록 없이 코드 수정이 시작되면 즉시 중단한다.
5. diff 기록은 전체 파일 또는 수정 구간을 포함해야 하며, 사용자가 즉시 롤백할 수 있어야 한다.

### 3.3 확정 범위 외 수정 금지

1. 이 문서의 화이트리스트 밖 파일은 수정하지 않는다.
2. 화이트리스트 밖 파일 수정이 필요하면 즉시 중단하고 사용자 승인을 받는다.
3. 인코딩, 포맷팅, import 정리, linter 자동 수정도 확정 범위 밖이면 하지 않는다.
4. 변경 목적과 직접 관련 없는 refactor는 금지한다.

### 3.4 UI 변경 정책

1. 현재 서비스와 동일한 UI 디자이너가 만든 것처럼 기존 컴포넌트, 간격, 버튼 형태, 색상, typography를 따른다.
2. `/src/components` 폴더는 원칙적으로 수정하지 않고 참고한다.
3. 다만 이번 기능은 `TemplateEditWorkspace`, toolbar, preview surface 내부 view state가 직접 관련되어 있어 아래 화이트리스트에 최소 예외 파일을 명시한다.
4. 예외 파일에서도 목적 외 UI 구조 변경, 색상 변경, 불필요한 컴포넌트 교체는 금지한다.
5. 새 랜딩, 설명 카드, 장식 요소를 추가하지 않는다.

### 3.5 MCP 테스트 의무

1. 후속 구현 실행마다 `chrome-devtools` MCP로 실제 브라우저에서 확인한다.
2. 후속 구현 실행마다 `supabase` MCP를 실행한다. DB 변경이 없더라도 `get_advisors(type="security")`와 `get_advisors(type="performance")` 중 최소 하나를 실행하고 결과를 기록한다.
3. DB schema/data 수정이 필요하면 MCP로 직접 적용하지 않는다. SQL을 작성해 사용자에게 제공하고, 사용자가 직접 실행하도록 한다.
4. 테스트 수행 결과는 이 문서 하단의 테스트 기록 또는 후속 diff 문서에 남긴다.
5. Chrome 테스트는 단순 DOM 존재 확인으로 끝내지 않고, 최소한 view 전환 시간, mutation 규모, `data-canvas-owner-item` selector, `data-selection-panel-tab`, `data-canvas-owner-view-mode`를 확인한다.

## 5. 서비스 독립성 설계 원칙

이번 기능은 처음부터 별도 서비스로 분리 가능한 단위로 설계한다. "현재 React 컴포넌트 안에 두는 것이 빠르다"는 이유로 도메인 경계를 무너뜨리지 않는다.

### 5.1 Canvas View Mode Contract Service

#### 기능 목적

`preview`, `position`, `metadata`, `metadata2` view mode의 식별자, 라벨, owner item, 내부 tab key, 접근 가능성, fallback 규칙을 한 곳에서 계약화한다.

#### 단독 서비스로서의 가치

상자 편집 캔버스 외 페이지가 같은 view mode 계약을 사용할 수 있다. 향후 캔버스 view mode를 API 상품처럼 외부에서 제어할 때도 같은 DTO를 재사용할 수 있다.

#### 책임 범위

- view mode union 정의
- owner item 이름 계약
- label/description 계약
- view mode normalize
- view mode별 독립 state namespace 생성

#### 비책임 범위

- React render
- DOM mutation
- auto-size 실행
- preview HTML build
- DB 저장

#### API 계약

```ts
export type TemplateCanvasViewMode = 'preview' | 'position' | 'metadata' | 'metadata2';

export type TemplateCanvasViewTabKey =
  | 'preview'
  | 'position'
  | 'metadata'
  | 'metadata2';

export type TemplateCanvasViewModeDefinition = {
  mode: TemplateCanvasViewMode;
  tabKey: TemplateCanvasViewTabKey;
  label: string;
  description: string;
  ownerItem: string;
  metadataVisualMode: boolean;
  runtimePreviewMode: boolean;
};

export type NormalizeTemplateCanvasViewModeInput = {
  value: unknown;
  fallback?: TemplateCanvasViewMode;
};
```

#### 데이터 소유권

이 서비스는 view mode 계약만 소유한다. 선택된 frame, draft HTML, preview HTML, overlay collapsed state는 소유하지 않는다.

#### 의존 서비스

없음. 순수 DTO/정규화 서비스로 유지한다.

#### 분리 배포 시 최소 조건

TypeScript DTO 또는 JSON schema로 계약을 export할 수 있어야 한다. React 없이 단독 unit test가 가능해야 한다.

### 5.2 Canvas Derived View Cache Service

#### 기능 목적

각 view 출력에 필요한 파생 상태를 content/layout/selection revision 기준으로 미리 계산하고, 탭 클릭 시 재계산 없이 꺼내 쓸 수 있게 한다.

#### 단독 서비스로서의 가치

상자 편집 캔버스의 느린 전환 문제를 UI가 아니라 view state materialization 문제로 분리한다. 향후 worker, server-side precompute, remote cache로 확장 가능하다.

#### 책임 범위

- view별 cache key 생성
- contentRevision, layoutRevision, selectionRevision, settingsSignature 관리
- position view 파생 상태: position group, edge topology snapshot, relative anchor plan, spacing guide plan
- metadata view 파생 상태: metadata marker plan, relation connector plan, review warning plan
- metadata2 view 파생 상태: metadata와 같은 초기 계산을 별도 namespace로 저장
- preview view 파생 상태: runtime preview cache key와 build 준비 상태 추적

#### 비책임 범위

- live DOM 직접 변경
- React state 직접 변경
- DB 저장
- button render

#### API 계약

```ts
export type TemplateCanvasViewRevision = {
  draftRevision: number;
  layoutRevision: number;
  selectionRevision: number;
  settingsSignature: string;
};

export type TemplateCanvasViewCacheKey = {
  templateId: string;
  viewMode: TemplateCanvasViewMode;
  revision: TemplateCanvasViewRevision;
};

export type TemplateCanvasDerivedViewState = {
  key: TemplateCanvasViewCacheKey;
  viewMode: TemplateCanvasViewMode;
  ready: boolean;
  stale: boolean;
  overlayPlan: unknown;
  domPatchPlan: unknown;
  diagnostics: {
    computedAt: number;
    reason: string;
  };
};
```

필수 guard API:

```ts
export type TemplateCanvasPreparedViewMatchResult =
  | { ok: true; preparedView: TemplateCanvasDerivedViewState }
  | {
      ok: false;
      reason:
        | 'view-mode-mismatch'
        | 'revision-mismatch'
        | 'settings-signature-mismatch'
        | 'not-ready'
        | 'stale';
      requestedViewMode: TemplateCanvasViewMode;
      preparedViewMode?: TemplateCanvasViewMode;
    };

export const assertPreparedViewMatchesRequest = (
  requested: TemplateCanvasViewCacheKey,
  prepared: TemplateCanvasDerivedViewState | null
): TemplateCanvasPreparedViewMatchResult;
```

`assertPreparedViewMatchesRequest(...)`가 `ok: false`를 반환하면 UI는 prepared view를 렌더하지 않는다. 이때 다른 view의 결과를 "임시로" 보여주는 fallback은 금지한다.

#### 데이터 소유권

파생 view state와 invalidation signature를 소유한다. canonical editor draft는 소유하지 않고 입력으로만 받는다.

#### 의존 서비스

- Canvas View Mode Contract Service
- Runtime Preview Service
- 기존 edge/topology 계산 함수는 직접 import보다 DTO adapter로 감싼다.

#### 분리 배포 시 최소 조건

입력 HTML 또는 canonical frame DTO를 받아 view별 derived DTO를 반환할 수 있어야 한다. DOM이 없어도 cache key와 invalidation 판단은 test 가능해야 한다.

### 5.3 Runtime Preview Build Service

#### 기능 목적

`미리보기` 진입 시점에 runtime HTML을 즉시 새로 만드는 대신 draft/layout 변경 시 background로 prebuild하고 cache한다.

#### 단독 서비스로서의 가치

실제 사용 미리보기는 별도 서비스/API 상품화 가능성이 높다. editor DOM과 runtime output의 책임을 분리해야 preview가 editor geometry를 오염시키지 않는다.

#### 책임 범위

- editor draft hash 계산
- runtime preview build input DTO 정의
- `buildTemplateUsagePreviewHtml` 실행 시점 제어
- preview HTML cache
- attachment/signature/runtime field 초기화 정책

#### 비책임 범위

- editor DOM 직접 수정
- `setPreviewHtml` 직접 호출
- owner button render
- DB 저장

#### API 계약

```ts
export type RuntimePreviewBuildInput = {
  templateId: string;
  editorDraftHtml: string;
  draftHash: string;
  layoutSignature: string;
  options: {
    stabilizeInitialLayout: boolean;
    preventInitialValueClearShrink: boolean;
    measurePeerClusterHeightTargets: boolean;
    measurePeerClusterWidthTargets: boolean;
  };
};

export type RuntimePreviewBuildResult = {
  cacheKey: string;
  runtimeHtml: string;
  reused: boolean;
  builtAt: number;
};
```

#### 데이터 소유권

runtime preview HTML과 build cache를 소유한다. editor draft HTML은 입력으로만 받는다.

#### 의존 서비스

- Canvas View Mode Contract Service
- Canvas Derived View Cache Service

#### 분리 배포 시 최소 조건

HTML string input과 options만으로 runtime HTML을 반환해야 한다. React component state에 의존하면 안 된다.

### 5.4 Canvas Tab Presentation Adapter

#### 기능 목적

서비스 계약을 실제 owner page 버튼과 canvas toolbar 버튼에 연결한다.

#### 비책임 범위

- view cache 계산
- DOM 정규화

## 7. 현재 코드 원인

### 7.1 view mode가 독립 tab 상태로 유지되지 않음

현재 view mode 타입은 `preview | position | metadata`뿐이다.

- `src/components/template/workspace/types.ts`
  - `SelectionPanelTab = 'metadata' | 'position'`
  - `TemplateEditWorkspaceCanvasViewMode = 'preview' | 'position' | 'metadata'`

`TemplateEditWorkspace`는 `canvasViewMode`를 다시 `selectionPanelTab`으로 축소한다.

```ts
const canvasViewSelectionPanelTab =
  normalizedCanvasViewMode === 'metadata' ? 'metadata' : 'position';
```

이 구조에 `속성2`를 `metadata`로 매핑하면 두 버튼이 같은 tab state를 공유하게 된다. 사용자가 지적한 치명적 설계 문제가 여기서 발생한다.

### 7.2 상위 owner 전환과 내부 tab 전환이 2단계로 발생

`src/app/canvas/page.tsx`의 `handleSelectCanvasViewMode`가 owner settings를 바꾸고, 이후 `TemplateEditWorkspace` 내부 effect가 `selectionPanelTab`을 따라 맞춘다. 이로 인해 상위 owner state와 preview surface state가 한 번에 바뀌지 않는다.

현재 경로:

1. owner root 버튼 click
2. `settings.canvasViewMode` 변경
3. `CanvasOwnedWorkspace` props 갱신
4. `TemplateEditWorkspace`에서 `canvasViewSelectionPanelTab` 계산
5. effect/layoutEffect에서 `setSelectionPanelTab`
6. heavy rehydrate/layout effect 실행

개선 방향:

- view mode 자체를 workspace의 제어 상태로 인정한다.
- `selectionPanelTab`은 view mode의 alias가 아니라 view rendering adapter가 읽는 값이어야 한다.
- `metadata2`는 `metadata`로 축소하지 않는다.

### 7.3 tab switch에서 auto-size와 peer edge 경로가 다시 돈다

현재 `applyEditorAutoSizeBoxesWithPreservedLayout(root)`는 root 전체에서 auto-height frame을 수집한다.

```ts
collectFrameSelectionAnchors(root)
  .filter((frameNode) => readFrameAutoHeightBox(frameNode))
```

이 함수는 `selectionPanelTab !== 'position'` 경로에서도 실행된다. 따라서 `속성` 탭으로 전환하는데도 auto-height frame 전체를 다시 측정할 수 있다.

`position` 경로에서는 다음 작업이 같이 실행된다.

- `materializePositionGroupWrappers`
- `ensureRelativeAnchorConfigs`
- `normalizePositionGroupRelativeAnchors`
- `applyRelativeAnchoredFrameRectsInRoot`
- `applyEditorAutoSizeBoxesWithPreservedLayout`
- `buildLiveEdgeTopologySnapshot`
- `TemplateEdgeSelectionService.reconcileSelectionState`

이들은 content/layout 변경 시 필요한 작업이지, 단순 tab switch마다 필요한 작업이 아니다.

### 7.4 HTML 재직렬화와 surface 재삽입

`extractPreviewRenderHtml(root)`는 live root의 `innerHTML`을 복사한 뒤 정규화, attachment materialize, transient UI strip, selection attr strip 등을 수행하고 HTML string을 반환한다.

이후 `setPreviewHtml(nextRenderHtml)`이 실행되면 `TemplateEditPreviewSurface`의 `dangerouslySetInnerHTML`이 다시 들어간다.

탭 전환 중 content/layout revision이 바뀌지 않았는데 HTML 재삽입이 발생하면 불필요한 DOM churn이 생긴다.

### 7.5 preview mode도 클릭 시 runtime HTML build가 발생할 수 있음

`canvasViewPreviewRequested`가 true이고 `templateUsagePreviewHtml`이 없으면 layout effect에서 다음 작업을 즉시 수행한다.

- `syncFormControlMarkup(root)`
- `extractEditorHtml(root)`
- `buildTemplateUsagePreviewHtml(editorDraftHtml, options)`
- `setTemplateUsagePreviewHtml(runtimeHtml)`

즉 `미리보기`도 preloaded view가 아니라 activation-time build에 가까운 경로가 남아 있다.

## 8. 설계 방향

### 8.1 view mode 확장

권장 타입:

```ts
type TemplateEditWorkspaceCanvasViewMode =
  | 'preview'
  | 'position'
  | 'metadata'
  | 'metadata2';
```

`SelectionPanelTab`을 그대로 확장할지, 별도 `TemplateCanvasViewTabKey`를 만들지는 구현 전 확정한다. 권장안은 아래와 같다.

```ts
type SelectionPanelTab = 'position' | 'metadata' | 'metadata2';
type TemplateCanvasViewTabKey = 'preview' | SelectionPanelTab;
```

`preview`는 실제 사용 출력 모드이므로 `SelectionPanelTab`으로 취급하지 않는 것이 안전하다.

### 8.2 button definition은 value-only 배열 금지

현재 owner page는 `canvasViewModeOptions`가 value/label만 가진다. 후속 구현에서는 owner item을 명시한다.

```ts
const canvasViewModeOptions = [
  {
    value: 'preview',
    label: '미리보기',
    ownerItem: 'canvas-page-root-button-미리보기',
    description: '실제 사용 화면',
  },
  {
    value: 'position',
    label: '크기 및 위치',
    ownerItem: 'canvas-page-root-button-크기-및-위치',
    description: '크기와 위치',
  },
  {
    value: 'metadata',
    label: '속성',
    ownerItem: 'canvas-page-root-button-속성',
    description: '키/밸류 속성',
  },
  {
    value: 'metadata2',
    label: '속성2',
    ownerItem: 'canvas-page-root-button-속성2',
    description: '키/밸류 속성',
  },
] as const;
```

주의:

- `속성2` description은 초기에는 `속성`과 같아도 된다.
- `ownerItem`은 label에서 자동 생성하지 않는다.
- grid는 4개 버튼 기준으로 조정한다. 예: `sm:grid-cols-4`.

### 8.3 내부 toolbar 설계

현재 내부 toolbar는 `미리보기`가 별도 버튼이고, `크기 및 위치/속성`은 edit settings tab group이다.

요구사항을 엄격히 반영하면 내부 toolbar도 같은 view mode definition을 사용한다.

권장:

- `미리보기`
- `크기 및 위치`
- `속성`
- `속성2`

모두 같은 view mode command를 발생시킨다.

주의:

- preview는 실제 사용 preview mode이므로 편집 overlay를 숨긴다.
- `metadata2`는 `metadata`와 같은 UI를 초기 출력하되 `selectionPanelTab === 'metadata2'`로 식별한다.
- button shape 계산은 index/length 기반으로 바꾼다. 현재는 2개 버튼 기준 `first/last`만 쓰므로 3개 이상에서 middle 처리가 필요하다.

### 8.4 tab-only switch에서 금지할 작업

content/layout/selection revision이 바뀌지 않은 단순 view mode 전환에서는 다음 작업을 실행하지 않는다.

- `applyEditorAutoSizeBoxesWithPreservedLayout`
- `applyTemplateAutoSizeBoxesWithPreservedLayout`
- `extractPreviewRenderHtml`
- `setPreviewHtml`
- `buildLiveEdgeTopologySnapshot`
- `materializePositionGroupWrappers`
- `applyRelativeAnchoredFrameRectsInRoot`
- `buildTemplateUsagePreviewHtml`
- 전체 frame 대상 `querySelectorAll('.v202-frame-group[data-template-frame-group]')` 반복

단, 아래 작업은 가볍게 허용한다.

- root `data-selection-panel-tab` 갱신
- root `data-canvas-owner-view-mode` 갱신
- view별 overlay layer visibility toggle
- active button class/aria 갱신
- 이미 계산된 overlay plan 적용

### 8.5 revision 기반 invalidation

탭 전환 최적화의 핵심은 "계산하지 않음"이 아니라 "변경된 것만 계산"이다.

권장 revision:

- `draftRevision`: editor HTML 또는 frame content가 바뀔 때 증가
- `layoutRevision`: frame position, size, auto-size result, edge/anchor 구조가 바뀔 때 증가
- `selectionRevision`: selected frame group ids 또는 edge selection이 바뀔 때 증가
- `metadataRevision`: frame metadata draft, relation role, value key가 바뀔 때 증가
- `previewRuntimeRevision`: runtime preview build input이 바뀔 때 증가

view별 invalidation:

| view | invalidation 기준 | 전환 시 실행 |
| --- | --- | --- |
| `position` | `layoutRevision`, `selectionRevision`, position settings signature | cache hit이면 overlay 표시만 |
| `metadata` | `metadataRevision`, `selectionRevision`, metadata settings signature | cache hit이면 marker/overlay 표시만 |
| `metadata2` | `metadata2Revision`, `selectionRevision`, metadata2 settings signature | metadata와 독립 cache hit 사용 |
| `preview` | `draftRevision`, `layoutRevision`, runtime preview options signature | cache hit이면 runtime HTML 교체 없이 표시 |

### 8.6 metadata2 독립성

`metadata2`는 다음을 `metadata`와 공유하면 안 된다.

- active tab value
- overlay collapsed state
- view cache key
- relation connector render signature
- metadata visual mode signature
- user interaction mode state

공유해도 되는 것:

- metadata calculation helper
- role option list
- button visual component
- validation helper
- DTO schema

즉, 함수 재사용은 허용하지만 상태 identity 공유는 금지한다.

### 8.7 교차 view cache 사용 금지

이 절은 사용자의 우려를 막기 위한 핵심 불변 조건이다. "이미 준비된 화면을 보여준다"는 말은 각 view가 자기 이름으로 준비한 결과만 보여준다는 뜻이다. 다른 view에서 준비한 결과가 비슷해 보여도 대체 출력으로 사용할 수 없다.

#### 8.7.1 원본 데이터와 출력 결과의 분리

공유 가능한 것은 canonical 원본 데이터뿐이다.

- template id
- editor draft HTML 또는 canonical frame DTO
- frame group id 목록
- 저장된 metadata 값
- 저장된 position/layout 값
- 선택된 frame group id

공유 금지 대상은 view별 출력 결과이다.

- `position`용 edge button plan
- `position`용 relative anchor/position group overlay plan
- `metadata`용 marker/relation connector/role overlay plan
- `metadata2`용 marker/relation connector/role overlay plan
- `preview`용 runtime HTML
- overlay collapsed state
- render signature
- DOM patch plan
- prepared view cache entry

따라서 구현자는 "같은 원본을 읽어 각 view가 독립 출력물을 만든다"는 구조를 지켜야 한다. "metadata 출력물을 metadata2에서도 잠깐 보여준다"는 구조는 금지한다.

#### 8.7.2 cache identity 불변 조건

prepared view를 렌더하기 전에는 반드시 아래 조건을 모두 만족해야 한다.

```ts
preparedView.key.viewMode === requestedViewMode
preparedView.viewMode === requestedViewMode
preparedView.key.revision.draftRevision === requestedRevision.draftRevision
preparedView.key.revision.layoutRevision === requestedRevision.layoutRevision
preparedView.key.revision.selectionRevision === requestedRevision.selectionRevision
preparedView.key.revision.settingsSignature === requestedRevision.settingsSignature
preparedView.ready === true
preparedView.stale === false
```

하나라도 실패하면 해당 prepared view는 렌더 금지다.

#### 8.7.3 cache miss 처리 규칙

cache miss 또는 mismatch가 발생하면 다음 순서로 처리한다.

1. 현재 클릭한 버튼의 active state는 즉시 해당 view로 바꾼다.
2. 요청한 view의 prepared view가 없으면 해당 view 전용 pending state를 표시하거나, 기존 현재 view를 유지하되 새 view 결과라고 표시하지 않는다.
3. 요청한 view의 계산을 시작한다.
4. 계산 결과의 `viewMode`가 요청한 view와 정확히 일치할 때만 렌더한다.
5. 다른 view의 cache를 fallback으로 사용하지 않는다.

금지:

- `metadata2` cache miss 시 `metadata` 결과를 렌더
- `metadata` cache miss 시 `metadata2` 결과를 렌더
- `position` cache miss 시 마지막 `metadata` DOM patch를 유지한 채 `position` active로 표시
- `preview` cache miss 시 editor draft HTML을 runtime preview 완료 결과처럼 표시

#### 8.7.4 함수 재사용과 state 공유의 경계

허용:

```ts
const metadata2PreparedView = buildMetadataLikePreparedView({
  viewMode: 'metadata2',
  source: canonicalEditorModel,
});
```

금지:

```ts
const metadata2PreparedView = metadataPreparedView;
```

허용:

```ts
const metadata2OverlayPlan = buildMetadataOverlayPlan({
  namespace: 'metadata2',
  source: canonicalEditorModel,
});
```

금지:

```ts
const metadata2OverlayPlan = metadataOverlayPlan;
```

`buildMetadataLikePreparedView` 같은 계산 함수는 공유 가능하다. 하지만 함수 입력의 `viewMode`, `namespace`, `cacheKey`, `renderSignature`는 반드시 view별로 다르게 들어가야 한다.

#### 8.7.5 실패 시 사용자에게 보이는 상태

prepared view mismatch가 발견되면 조용히 옆 view를 보여주지 않는다. 후속 구현자는 아래 중 하나를 선택해야 한다.

- 해당 view 계산이 끝날 때까지 view surface를 pending 상태로 둔다.
- 기존 view surface를 유지하되 active 전환 완료처럼 보이지 않게 한다.
- 개발 모드에서는 mismatch reason을 console/debug panel에 기록한다.

어떤 경우에도 `속성2` 버튼이 active인데 실제 DOM이 `metadata` prepared view라는 상태를 만들면 안 된다.

#### 8.7.6 브라우저 검증 기준

Chrome MCP 테스트는 단순히 버튼이 보이는지 확인하지 않는다. 아래를 반드시 확인한다.

- `metadata` 클릭 후 rendered prepared view의 `data-canvas-prepared-view-mode`가 `metadata`인지 확인
- `metadata2` 클릭 후 rendered prepared view의 `data-canvas-prepared-view-mode`가 `metadata2`인지 확인
- `metadata2` cache를 비운 상태에서 `metadata` cache가 있어도 `metadata` 결과가 렌더되지 않는지 확인
- `metadata`와 `metadata2`의 overlay collapsed state를 각각 변경한 뒤 서로 영향을 주지 않는지 확인
- mismatch 상황에서 `assertPreparedViewMatchesRequest(...)`가 `view-mode-mismatch`를 반환하는지 확인

권장 DOM attribute:

```html
<div
  data-canvas-prepared-view-mode="metadata2"
  data-canvas-prepared-view-cache-key="..."
/>
```

이 attribute는 테스트와 디버깅을 위한 계약이다. 자동 생성 이름에 의존하지 않는다.

### 8.8 preview prebuild

현재 preview mode는 진입 시 runtime HTML을 만들 수 있다. 개선 후에는 다음 흐름을 사용한다.

1. draft/layout 변경 발생
2. runtime preview input hash 계산
3. idle task 또는 debounced task로 `RuntimePreviewBuildService.prebuild(input)` 실행
4. `preview` 버튼 클릭 시 cache hit 확인
5. cache hit이면 `templateUsagePreviewHtml`을 새로 build하지 않음
6. cache miss이면 fallback으로 build하되, 버튼 active 표시는 먼저 반영하고 build pending state를 명시적으로 관리

금지:

- preview 진입만으로 editor geometry를 수정하지 않는다.
- runtime preview auto-size 결과를 editor draft layout에 자동 commit하지 않는다.

## 10. 금지 구현 예시

아래 구현은 금지한다.

```ts
// 금지: 속성2를 metadata alias로 둠
{ value: 'metadata', label: '속성2' }
```

```ts
// 금지: metadata2를 metadata로 normalize
value === 'metadata2' ? 'metadata' : value
```

```ts
// 금지: view mode마다 독립 상태 없이 metadata UI만 조건 추가
const isMetadataLike = selectionPanelTab === 'metadata' || selectionPanelTab === 'metadata2';
const activeMetadataState = metadataState;
```

```ts
// 금지: metadata2 요청에서 metadata cache를 fallback으로 사용
const preparedView =
  cache.get(requestedMetadata2Key) ||
  cache.get(metadataKey);
```

```ts
// 금지: cache payload의 실제 viewMode를 확인하지 않고 렌더
if (preparedView.ready) {
  renderPreparedView(preparedView);
}
```

```ts
// 허용되는 형태: 요청 view와 prepared view identity가 정확히 일치할 때만 렌더
const match = assertPreparedViewMatchesRequest(requestedKey, preparedView);
if (match.ok) {
  renderPreparedView(match.preparedView);
} else {
  renderPreparedViewPendingState(match.reason);
}
```

`isMetadataLike` helper는 렌더 함수 재사용에는 사용할 수 있지만, state/cache/signature identity를 공유하는 근거로 쓰면 안 된다.
